## 1. 確かめ方と、その限界

**レイアウトの崩れは起きていない。** 画面の大きさを 360x640（小さめの端末）と 411x731（Pixel 相当）に固定し、
AI が返しうる最長の文（設計書 §3.3 の例文「立って、座面に手を添えたまま。相手が座るまでそこで待ってください」＋長い理由文）を
入れて全画面を組み直したところ、はみ出しは1件も出なかった（`mobile/test/layout_test.dart`）。
文字があふれて読めない、という類の問題ではない。

**エミュレータでの目視はできていない。** Pixel 6 API 35 は起動したが、`adb` の大きいファイル転送が
この PC で繰り返し停止し、APK を入れられなかった。したがって以下は、実装を読んで辿った体験であり、
色や余白の見え方についての指摘は含まない。**実機で触った人の印象のほうが、この点では確かである。**

**生成の速さは問題ではない。** 本番の API で実測して、ステップ1が約2.1〜3.0秒、ステップ2が約1.6〜3.1秒だった。

## 2. 重い順の指摘

### 2-1. 何も起きない時間があり、動いている合図がない

体験の骨格に一番効いている。**待ちの画面が4つあり、どれも一文が置いてあるだけで、他に何も無い。**

| 画面 | 待つもの | 最長 | 置いてあるもの |
| :--- | :--- | :--- | :--- |
| 読み取っています | ステップ1の生成 | 45秒 | 一文のみ。**ボタンが1つも無い** |
| 発信の準備をしています | 封緘とBLE開始 | 45秒 | 一文のみ。**ボタンが1つも無い** |
| 動作を用意しています | BLE接続＋ステップ2 | 55秒 | 一文と［ やめる ］ |
| いまは近くにいません | スキャン | 無期限 | 一文と［ 閉じる ］ |

前の2つは `const Sheet(body: Lead('…'))` で、押せるものが画面に存在しない
（`mobile/lib/screens/receiver.dart:178,180`）。Android の戻るジェスチャーは効くが、それは流れごと抜ける操作で、
「待つのをやめたい」ではなく「最初からやり直す」になる。

設計書 §3.3 が「スピナーも進捗も置かない」と書いたのは、**受け手の待機画面**についてである。
あれは「近くに3人います」のような偽の希望を出さないための決まりであって、サーバ往復の2〜3秒に当てはめる話ではなかった。
実装で広げすぎた。

**直し方。** 待ちの画面に控えめな動き（点の明滅程度）を置く。3秒を超えたら「まだ待っています」を添える。
少なくとも読み取り中と準備中に［ やめる ］を置き、押せるものが1つも無い画面を無くす。

### 2-2. 「いまは近くにいません」が、嘘になる場面がある

譲る側がアプリを開き、Bluetooth がオフだったり権限を拒否したりした場合、画面はこうなる。

```
いまは近くにいません                      ← 26px

（中略）

Bluetooth の権限が無いと近くの人を見つけられません   ← 13px の灰色、最下部
```

大きい文字が「近くに誰もいない」と言い、実際には**スキャンすら始まっていない**
（`mobile/lib/screens/giver.dart` の `_scanning()`）。利用者は「今日は誰もいないのか」と受け取ってアプリを閉じる。
同じ構造が受け手の需要の宣言画面にもあり、サーバに繋がらないときのエラーが同じ大きさで最下部に出る。

設計書 §3 は「階層は文字サイズだけで作る」と決めた。その決まりに従った結果、
**一番大事な事実が一番小さい文字になっている。**

**直し方。** 原因があるときは主メッセージ自体を差し替える。「Bluetooth をオンにしてください」を 26px で出し、
「いまは近くにいません」はスキャンできているときだけに限る。

### 2-3. 権限のダイアログが、説明なしに最大4連発で出る

役割を選んだ瞬間に `requestPermissions` が走り、システムのダイアログが順に出る
（`mobile/android/…/MainActivity.kt`）。何のために要るのかを伝える画面が手前に無い。
開発計画のフェーズ4に「初回に理由を1文で出す」と書いたが、実装していない。**こちらの抜けである。**

さらに、**役割ごとに要る権限が違うのに、両方から全部を要求している。**

| 役割 | 実際に要る | いま要求している |
| :--- | :--- | :--- |
| 譲る側 | SCAN、CONNECT | SCAN、CONNECT、**ADVERTISE**、**通知** |
| 受け手 | ADVERTISE、CONNECT、通知 | ADVERTISE、CONNECT、通知、**SCAN** |

このアプリは「露出を最小にする」ことを企画の柱に置いている（設計書 §1.4）。
要らない権限まで最初に求める作りは、その説明と噛み合わない。審査で突かれると弱い。

**直し方。** 役割ごとに必要な権限だけを求める。直前に1文の説明を挟む。

### 2-4. 譲ったあと、譲る側に「終わった」出口が無い

動作の提示画面（`_action()`）にある操作は［ やめる ］だけで、
受け手が［ ありがとう ］を押さない限り画面は変わらない。

実際に立って席を渡したのに受け手が押し忘れると、譲る側は立ったまま画面を見続けることになり、
**唯一の逃げ道が［ やめる ］＝取り消し**（受け手に cancel が飛ぶ）になる。譲った人が「取り消す」を押す以外にない。

設計書 §2.5 は、混雑時に「うまくいかなかったかもしれません。座り直しても大丈夫です」を出すと決めていた。
今回スコープから外した結果が、この行き止まりである。**文言はすでに設計書にあるので、置くだけで塞がる。**

### 2-5. 選んだ項目をもう一度押すと、選択が外れて先へ進めなくなる

需要の宣言（4択）と混み具合（3択）の両方で、選択済みの項目をもう一度押すと選択が解除される
（`receiver.dart` の `_declare()`、`giver.dart` の `_scanning()`）。
解除できることはどこにも書いていない。押した本人には「さっきまで押せた［ 譲る ］が灰色に戻った」としか見えない。

**直し方。** 単一選択は選び直しだけにして、解除を無くす。

### 2-6. 無効になっている主ボタンが、なぜ押せないかを言わない

［ つづける ］と［ 譲る ］は条件を満たすまで灰色で、理由の表示が無い。
2-5 と重なると「押しても何も起きないボタン」に見える。

### 2-7. 起動画面が、製品より注記のほうが重い

上半分は 96px の余白とボタン2つ、下半分は説明1行＋注記2行＋審査用リンクで、**情報量が下に偏っている。**
アプリの名前もどこにも出ない。初めて開いた人が最初に読むのが制約の説明になっている。

審査用リンクが製品の入口に同居している点も、POSTMORTEM 根本原因4（デモ操作と製品画面を分けていなかった）が
警告した形に近い。注記そのものは AGENTS.md §5 が要求しているので消せないが、**置き方は変えられる。**

**直し方。** 制約の注記は初回起動時だけに出す、もしくは1行に縮めて、2回目以降は設定の奥へ移す。

### 2-8. 「そっと伝わりました」が4秒で消え、直後に「いまは近くにいません」に戻る

主役への唯一の報酬（設計書 §3.3）が数秒で流れ、スキャン画面へ自動で戻る。
戻った先はたいてい「いまは近くにいません」で、余韻が残らない。

**直し方。** ここは自動で閉じず、［ 閉じる ］を置いて役割選択へ戻す。

## 4. 直さないほうがよいもの

念のため書いておく。**受け手の待機画面に進捗を出さないのは正しい。**
「近くに3人います」を出さないという判断（設計書 §2.2）は、誰も譲らなかったときに残酷になるためで、
2-1 の指摘はこの画面を含まない。ここに動きを足すと、成立を約束することになる。
