譲る側が「相手は本当に席を必要としているのか」を判断せずに済むこと。これを機能で保証するのが本書の中心的な仕事である。無言化はその上に乗る。

## 0. この文書の読み方

各要件には「対応する要求」列がある。要求定義書の節番号か、§5 の体験のステップ番号を指す。**対応する要求を書けない要件は載せない。** コンセプトから外れた機能が紛れ込むのを防ぐ歯止めである。

用語は2つだけ。座席にいて席を渡す側を**譲る側**、席を必要としている側を**受け手**と呼ぶ。v1.0 の「サポーター」「リクエスター」がそれぞれこれに対応する。

FR番号は v1.0 から引き継いでいる。廃止した番号は欠番のまま残し、再利用しない。旧版の[`設計書.md`](設計書.md)を参照する際の混乱を避けるためである。

## 1. 機能要件

### 1.1 接続と近接検知

| ID | 要件 | 対応する要求 |
| :--- | :--- | :--- |
| FR-01 | 利用者に識別子を入力させない、画面に見せない、他人に伝えさせない。合言葉・QRコードの提示・号車番号の申告のいずれも要求してはならない | §3（一度も言葉を交わさない）。識別子の手渡しはそれ自体が対面コミュニケーションであり、ミッションと矛盾する |
| FR-14 | 端末同士の近接（数m以内）を自動で検知し、その範囲内に限ってマッチングすること。受け手・譲る側の双方が発信し、双方がスキャンする | §5 ステップ3・6（相手が「ごく近く」にいることが体験の前提）。隣接に限れば横断移動と席のキープが不要になる |
| FR-16 | 受け手が需要を宣言する手段を2通り用意すること。慢性的に必要な人は一度の設定で継続し、一時的に必要な人は乗車ごとに宣言する | §1（つわり・貧血は一時的だが、内部障害のように常時のものもある）。佐藤は今日だけ必要な側にあたる。慢性の利用者に毎回の操作を強いてはならない |

FR-01 が禁じているのは利用者に識別子を運ばせることであって、システム内部で識別子を使うことではない。近接検知に使うトークンは機械が生成・交換し、画面には一度も出さない。

### 1.2 譲る側の機能

主役の側なので、ここが本書でもっとも厚い節になる。

| ID | 要件 | 対応する要求 |
| :--- | :--- | :--- |
| FR-02 | 起動時に「席がほしい」「いま座っている」のいずれかを選べること。**選択肢に「譲れる」のような善意を含意する語を使わないこと** | §2（ペルソナが2種類存在する）。§3（善意を搾取しない）。善人認定を含意すると、選ぶ時点で義務感が生じる |
| FR-04 | 譲ると決める操作の中で、その場の混雑度を1タップで報告できること | §5 ステップ4、§4 AI-2。混雑度は座って車内を見ている譲る側が最も正確に把握でき、慢性設定の受け手には報告手段がない |
| FR-07 | 譲ると決めた際、AIが生成した身体動作と理由を受信できること | §5 ステップ5、§4 AI-2／AI-3 |
| FR-17 | 譲ると決めた後に取り消せること。理由を求めず、確認を挟まず、席へ戻ってよいと明示すること | §5「譲らない選択も体験の一部である」。囲まれていた・降車駅だった・また固まった、はいずれも起こる |
| FR-09 | 譲らずに画面を閉じた場合、何も起こらないこと。受け手に通知せず、記録も残さないこと | §3（無言のミッションを、譲らない場面でも維持する）。**辞退ボタンは設けない** |

ここでは、機能を足さないことそのものが要件になっている。譲る側が画面を閉じるだけで成立する「不可視のノー」を、余分な確認ダイアログや辞退ボタンで壊さないために明文化しておく。

FR-08（キープ時に画面全体を緑色に点灯させる）は**廃止した。** 発光して席の前に立ちはだかる動作は、声をかける恥ずかしさを無言で目立つ恥ずかしさに置き換えるだけになる。近接検知の導入で横取り防止の役目も不要になった。混雑時の横取り対策は FR-07 が返す身体動作（座面に手を添えて待つ）が担う。

FR-15（近くに需要があることを静かに知らせる受動サイン）も**廃止した。** これには端末が背景で近接検知を続ける必要があるが、iOS の背景スキャンは間隔が疎で予測不能であり、1デバイスにつき単発の通知しか届かない。Android では実現しうるものの、「Android なら気づけるが iPhone では気づけない」というプラットフォーム差は体験の説明を壊す。**プル型（譲る側が自分でアプリを開く）に一本化する。**

この廃止には副作用として利点がある。背景でのスキャンが要件から消え、残るのは受け手の背景での発信だけになった。片側だけが背景対応で済む。

### 1.3 受け手の機能

| ID | 要件 | 対応する要求 |
| :--- | :--- | :--- |
| FR-03 | よくある状態をワンタップで選べ、必要なら自由記述（最大100字）を添えられること | §5 ステップ1、§4 AI-1 |
| FR-05 | 譲る側が決めた直後に、ごく近くで席が空くことを受け取れること。特定の人物を指し示す表示や、車内を横断させる案内を出してはならない | §5 ステップ6。近接検知が隣接を保証するので、目視で足りる |
| FR-18 | 常時設定の受け手に対しては、譲る側の申し出を受ける前に、今も席が必要かを確認すること | §2（慢性設定は古くなる。すでに座っている人へ申し出が飛ぶと空振りする） |
| FR-06 | 着席後、ワンタップで譲る側にお礼を送れること。文字によるメッセージ入力は設けないこと | §5 ステップ8 |
| FR-10 | 席が見つからなかった場合、または第三者が座ってしまった場合に、1タップで再探索へ戻れること | §1（横取りは「善意が実らない」構造そのもので、発生時の回復手段が要る） |

お礼のタップは装飾ではない。目線も合わせない体験にすると受け渡しの瞬間に社会的な負債が宙に浮き、どちらかが耐えきれず会釈してしまう。お礼のタップがその負債を吸収するので、両者が会釈から解放される。往復を防ぐため一方向に限り、譲る側から返す手段は設けない。

### 1.4 AIと安全

| ID | 要件 | 対応する要求 |
| :--- | :--- | :--- |
| FR-11 | 2段階のAIパイプラインで処理すること（ステップ1：状態→Needs、ステップ2：Needs＋混雑度→Handoff） | §4 AI-1・AI-2 の責務分担 |
| FR-12 | AIの出力に発話ワードが含まれた場合、サーバー側で強制的に安全な固定文へ差し替えること | §4.1（発話指示を一切含めてはならない）。§0 の「声をかけられないまま」を直接守る最重要要件であり、AI任せにしない |
| FR-13 | 混雑度によって身体動作がどう変わるかを、並べて確認できる画面を用意すること。製品の導線からは分離すること | §4 AI-2 の必然性を審査側に示すため。動いていることを目撃できなければ、実装してあっても伝わらない |

FR-12 だけは他の要件と性質が違う。他が体験の質を上げる要件である一方、これはプロダクトの存在理由が壊れることを防ぐ最後の砦にあたる。実装は前身から移植済み（`lib/speech.ts`／`lib/fallback.ts`）で、回帰テストも揃っている。

## 2. 非機能要件

| ID | 項目 | 要求仕様 | 対応する要求 |
| :--- | :--- | :--- | :--- |
| NFR-01 | 応答速度 | AI生成は1.5秒以内 | §5 の体験は電車が動いている数分の間に完結する前提であり、待ち時間がミッションを破綻させない範囲に収める |
| NFR-02 | 端末間遅延 | 譲る側の操作が受け手に届くまで0.5秒以内 | §5 ステップ6。譲る側が立ち上がるより先に受け手の画面が反応していなければ、目視で追えない |
| NFR-03 | プライバシー | 疾患名・障害名・氏名・顔写真を収集・保存・送信しない。位置情報を送信しない。近接検知に使う識別子は一定時間で更新し、追跡に使えないようにする。発信は電車の移動を検知している間に限る。受け渡し完了後に要請データを破棄する | §4.1 をデータ設計全体に拡張適用する。加えて、需要の発信そのものが受け手の脆弱性を露出させるため、露出の時間と粒度を最小化する |
| NFR-04 | UIデザイン | 同じコンポーネントを機械的に反復しない。説教くさい説明文やスライド用のキャッチコピーをUIに含めない。**様式（「駅サイン基調」など）は指定しない** | §0 のコンセプトを、製品として触ったときに安っぽく見せない。前身は様式を掲げたうえで同一角丸パネルの反復に着地しAIっぽいと指摘された（POSTMORTEM 根本原因5）ため、様式ではなく構造の禁止事項で縛る。具体的なルールは[`設計書.md`](設計書.md) §3 |
| NFR-05 | 稼働環境 | ネイティブアプリ。スマートフォンの縦画面に最適化。**当面のマッチング動作保証は同一OS間（iOS↔iOS、Android↔Android）に限る。今回作るのは Android のみとし、iOS は次フェーズへ回す** | FR-14 の近接検知はブラウザでは実現できない（[`設計書.md`](設計書.md) §1.3）。同一OSに限る理由は §1.5.1、Android を先にする理由は §7.1 |

NFR-03 は v1.0 から最も大きく変わった。疾患情報を送らないという原則は据え置いたうえで、近接検知の導入によって新たに生じた露出（近くの端末に「席を必要としている人がいる」と分かること）へ対策を足している。識別子の更新とモーションゲートがその中身で、いずれも接触確認アプリで実績のある手法である。

## 3. スコープ外

ビーコンなどの専用ハードウェアは作らない。近接検知はスマートフォン内蔵の無線で足りるため、v1.0 で Phase 2 としていた専用機器の必要性そのものが消えた。

ユーザー認証・会員登録は設けない。決済やポイント等のインセンティブ機能も設けない。いずれも §0 のコンセプトの達成に必須ではない。

号車をまたいだマッチングは扱わない。FR-14 が数m以内に限る設計なので、そもそも車両の境界を意識する必要がない。

**iOS 版は今回作らない。** 動作保証を同一OS間に絞った結果、デモは Android 2台で撮れるようになった。デモ動画のどのカットにも iOS が映らないため、[`AGENTS.md`](../AGENTS.md) のスコープ判断に従って外す（[`設計書.md`](設計書.md) §7.1）。UI は Flutter で書くので、iOS へ進む際に画面の作り直しは発生しない。

追加すべきという意見が出た場合は、まず「コンセプトのどの部分を満たすために必要か」を説明できるかで判断する。
