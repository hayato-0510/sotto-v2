## 0. この文書の読み方

各要件には「対応する要求」列があり、要求定義書の節番号・シナリオのステップ番号・
ミッション文のいずれかを指す。**対応する要求を書けない要件は、この文書に載せない**
（要求定義書§0のコンセプトに資さない機能を増やさないため）。

## 1. 機能要件（Functional Requirements）

### 1.1 端末間通信・接続機能

| ID | 要件 | 対応する要求 |
| :--- | :--- | :--- |
| FR-01 | 見知らぬ乗客同士にID（合言葉）を手入力させてはならない。デモでは自動的に同一の「デモ車両」に接続すること | 要求定義書§3（コアミッション：一度も言葉を交わさない）。合言葉の手入力はそれ自体が対面コミュニケーションであり、ミッションと矛盾する |
| FR-02 | アプリ起動時に「席を必要としている」か「座席に座っている（譲れる）」のいずれかを選択できること | 要求定義書§2（ペルソナが2種類存在する） |

### 1.2 リクエスター機能

| ID | 要件 | 対応する要求 |
| :--- | :--- | :--- |
| FR-03 | よくある状態（「つわり・めまい」「足腰の怪我」「内部疾患」）をワンタップで選択でき、必要に応じて自由記述（最大100字）できること | 要求定義書§5 シナリオ1（佐藤さんが状態を選択して要請する）、§4 AI-1 |
| FR-04 | 混雑度（空いている／混雑／超満員）を指定できること | 要求定義書§5 シナリオ1、§4 AI-2（混雑度に応じた動作生成の入力） |
| FR-05 | サポーターが席をキープした際、「緑色に光る人の前へ」という案内と席位置が表示されること | 要求定義書§5 シナリオ4 |
| FR-06 | 着席後、ワンタップでサポーターにお礼通知を送信できること | 要求定義書§5 シナリオ7 |

### 1.3 サポーター機能

| ID | 要件 | 対応する要求 |
| :--- | :--- | :--- |
| FR-07 | 要請が発生した際、AIが生成した「状況に応じた身体動作」を受信できること | 要求定義書§5 シナリオ2、§4 AI-2/AI-3 |
| FR-08 | ［ 席をキープする ］を押すと、画面全体が鮮やかな緑色に点灯し、目印として機能すること | 要求定義書§5 シナリオ3 |
| FR-09 | ［ 今は難しい ］を押した場合、理由を求めず、リクエスターにも通知せず、即座に次のサポーターへリレーすること | 要求定義書§3（無言のミッションを、辞退の場面でも維持する） |
| FR-10 | 万が一、第三者が強引に座ってしまった場合、［ 別の人が座ってしまった ］ボタンでリクエスターに再探索を通知できること | 要求定義書§1（横取りは背景で述べた「善意が実らない」構造そのものであり、発生時の回復手段が要る） |

### 1.4 AI・システム機能

| ID | 要件 | 対応する要求 |
| :--- | :--- | :--- |
| FR-11 | 2段階AIパイプライン（ステップ1：状態→Needs、ステップ2：Needs＋混雑度→Handoff）で処理すること | 要求定義書§4 AI-1・AI-2の責務分担 |
| FR-12 | AIの出力に発話ワードが含まれた場合、サーバー側で強制的に安全な固定文へフォールバックすること | 要求定義書§4.1（発話指示を一切含めてはならない）。ここは§0のコンセプトの「声を出さずに」を直接守る最重要要件であり、AI任せにしない |
| FR-13 | 混雑度「空いている」と「混雑時」で、AIが出す身体動作（離れる vs キープする）がどう変わるかを画面上で比較できること | 要求定義書§4 AI-2の必然性を審査側に示すための要件（AI-2が「本当に機能しているか」を目撃可能にする） |

## 2. 非機能要件（Non-Functional Requirements）

| ID | 項目 | 要求仕様 | 対応する要求 |
| :--- | :--- | :--- | :--- |
| NFR-01 | 応答速度 | AI生成時間は1.5秒以内 | 要求定義書§5のシナリオは「電車が動いている数分の間」に完結する前提であり、待ち時間がミッション（声を出さずに済ませる）自体を破綻させない範囲に収める |
| NFR-02 | 端末間遅延 | スマホAの操作がスマホBに届くまでの遅延は0.5秒以内 | 要求定義書§5 シナリオ2（「ピコンと控えめな通知が届く」という体験の即時性） |
| NFR-03 | プライバシー | 疾患名・障害名・顔写真を収集・保存・送信しない。要請データは受け渡し完了後に自動破棄 | 要求定義書§4.1（AIの非目標）を、システム全体のデータ設計にも拡張適用する |
| NFR-04 | UIデザイン | 駅の案内サインを基調としたミニマルな意匠。説教くさい説明文やスライド用キャッチコピーをUIに含めない | 要求定義書§0のコンセプトを、製品として体験する際に安っぽく見せないための要件 |
| NFR-05 | 稼働環境 | スマートフォンのブラウザ（iOS Safari / Android Chrome）の縦画面に最適化 | 要求定義書§2のペルソナが、電車内でスマホの片手操作を行う前提 |

## 3. スコープ外（Out of Scope）

* ビーコン機器などの追加ハードウェア開発（Phase 2構想。設計書§2.3参照）。
* ユーザー認証（ログイン）・会員登録機能。
* 決済やポイント等のインセンティブ機能。

これらは要求定義書§0のコンセプトの達成に**必須ではない**ため、今回のスコープに含めない。
（含めるべきという意見が出た場合は、まず「コンセプトのどの部分を満たすために必要か」を
説明できるかを基準に判断する。）
