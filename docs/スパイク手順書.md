## 0. 着手前に読むこと

### スパイクのコードは捨てる

ここで書くコードは**測定のための使い捨てである。** 製品に流用しない。スパイク用のブランチか、`spike/` のような明確に分離したディレクトリで書き、結果が出たら消すか凍結する。

理由は前身の失敗の形にある。「動いたコード」はそのまま製品へ流れ込みやすく、流れ込んだ時点で「measurement のための雑な作り」が製品の土台になる。measurement と実装は目的が違う。

### 「だいたい動いた」で通したことにしない

各スパイクには数値の合格基準を置いてある。**基準を満たしたかどうかを数値で記録する。** 「なんとなく動いた」「たぶん大丈夫そう」は不合格として扱う。判断に迷う結果が出た場合は、迷ったこと自体を記録する。

### 結果はここに書く

`docs/spike-results.md`（新規）に、条件・数値・判定を残す。**通った場合も残す。** 後から「なぜこの閾値なのか」を追えるようにするためで、これは[`設計書.md`](設計書.md) §8.2 の Issue 駆動と同じ趣旨である。

## 1. 用意するもの

**Android 実機2台。** Android 8.0 以降。BLE 5.0 対応が望ましいが必須ではない。エミュレータでは BLE を扱えないので実機が要る。

**スパイク用アプリ。** 必要な画面は次で足りる。

```
［ 発信を開始 ］ ［ 停止 ］
［ スキャンを開始 ］ ［ 停止 ］

＜ログ表示＞  時刻 / 検出したトークン / RSSI
［ CSVで書き出す ］
```

UI は問わない。[`設計書.md`](設計書.md) §3 の引き算のルールは製品側の話であり、スパイクには適用しない。

**測定用のメジャー。** 距離を目分量で取ると、後から数値の意味が消える。

## 2. スパイク1：RSSI で「隣接」と「離れている」を区別できるか

**問い。** 譲る側の端末が拾った RSSI から、3m以内と5m以上を区別できるか。

**なぜ最優先か。** 隣接限定（[`設計書.md`](設計書.md) §1.2）が設計全体の土台になっている。区別できなければ「すぐ近くに、席を必要としている人がいます」という表示が嘘になり、[`設計書.md`](設計書.md) §1・§2 の前提が崩れる。

### 手順

1. 端末A を発信、端末B をスキャンに設定する。サービス UUID は固定の1つでよい
2. 距離を **0.5 / 1 / 2 / 3 / 5 / 8 / 10 メートル**に固定し、各30秒ずつ RSSI を連続記録する
3. 次の条件それぞれで、全距離を繰り返す
   - 見通し（何もない廊下）
   - 端末A をズボンのポケットに入れる（布1枚）
   - 端末A をカバンの中に入れる
   - 端末A と B の間に人が1〜2人立つ
   - 実際の電車内（空いているとき・混雑しているとき）
4. 条件と距離の組ごとに、RSSI の**中央値と四分位範囲**を出す
5. **送信出力を最小（`ADVERTISE_TX_POWER_ULTRA_LOW`）にして、2〜4 を繰り返す**

手順5は保険ではなく、本命になりうる。RSSI の閾値で距離を推定するより、**送信出力を絞って物理的に到達範囲を数mに限るほうが頑健**な可能性がある。届いた時点で近い、と言い切れるなら閾値の調整が要らなくなる。両方を測ってから決める。

### 合格基準

- 見通しで、1m と 5m の RSSI 中央値の差が **15dBm 以上**あり、分布が重ならない
- ポケットに入れた状態でも、1m と 5m の差が **10dBm 以上**ある
- 混雑した電車内で「3m以内」を判定できる閾値が存在し、**誤り率20%以下**に収まる

### 落ちたとき

送信出力を絞る方式（手順5）で合格基準を満たせるなら、そちらを採用して RSSI 閾値を捨てる。どちらも駄目なら隣接限定そのものを見直すことになり、[`設計書.md`](設計書.md) §1.2・§2 と §9-1 のリスクに戻る。**このとき勝手に「まあ動くだろう」で先へ進まないこと。**

## 3. スパイク2：背景での発信は何分続くか

**問い。** 受け手のアプリを背景に置き、画面を消し、ポケットに入れた状態で、発信が何分続くか。モーションゲートと併用できるか。

**なぜ重要か。** 受け手がスマホをしまえることが体験の前提になっている（[`設計書.md`](設計書.md) §2.2）。続かなければ「しまえる」が崩れ、受け手に画面を開いたままにさせる設計へ変更せざるをえない。

### 手順

1. 端末A で発信を開始し、画面を消してポケットに入れる
2. **5分 / 15分 / 30分 / 60分**の時点で、端末B からスキャンして検出できるかを確認する
3. **Foreground Service ありと、なしの両方**で 1〜2 を実施する
4. Doze を強制した状態（`adb shell dumpsys deviceidle force-idle`）でも確認する
5. モーションゲートを併用し、静止 → 移動 → 静止で発信が正しく始まり止まるかを見る

### 合格基準

- 乗車時間として現実的な **30分間**、検出できる状態が続く
- モーションゲートが移動の検知で発信を始め、停止後 **1〜2分**で止める

### 予想される発見（設計に跳ね返る）

Android の Foreground Service は**永続通知の表示が必須**である。[`設計書.md`](設計書.md) §2.2 は「譲る側への通知は一切ない」と書いているが、これは**譲る側への打診**の話であり、**受け手自身の「発信中」表示**とは別物になる。むしろ NFR-03 の「発信中であることを常に画面に示す」と整合する。

とはいえ書きぶりの調整は要る。**Foreground Service が必須と判明した場合は、§2.2 と NFR-03 に「受け手側には常駐通知が出る」と明記すること。** 通知が一切ないと読める文言を残したまま実装すると、後から矛盾に見える。

### 落ちたとき

Foreground Service を必須とし、常駐通知の文言を「席がほしい、と発信中」にする。[`設計書.md`](設計書.md) §3.3 の待機画面の文言と揃える。

## 4. スパイク3：2台間の GATT で Handoff を直接渡せるか

**問い。** 譲る側と受け手が GATT で接続し、Handoff（動作・所要秒数・理由を含む数百バイトの JSON）を0.5秒以内に渡せるか。

**なぜ重要か。** 成立すれば**リアルタイムサービスが丸ごと不要になる**（[`設計書.md`](設計書.md) §7.2）。NFR-02 の0.5秒がローカルで自明に満たされ、Pusher や Supabase の選定そのものが消える。前身が踏んだサーバレスの状態共有の問題も回避できる。

### 手順

1. 受け手を GATT サーバ、譲る側を GATT クライアントにする
2. 譲る側から接続し、Handoff を書き込む
3. **接続の確立から書き込み完了まで**の時間を20回計測する
4. Wi-Fi や他の BLE 機器が多い環境でも計測する
5. 発信・スキャンと GATT 接続が同時に走って壊れないかを確認する

手順5を省かないこと。実際の利用では、受け手は発信しながら接続を受けることになる。片方ずつ試して両方動いたからといって、同時に動く保証はない。

### 合格基準

- 接続から書き込み完了までの**中央値が0.5秒以内**、95パーセンタイルで1秒以内
- 20回中 **18回以上**成功する
- 発信・スキャンと同時に動かしても、どちらも停止しない

### 落ちたとき

サーバ経由に戻す。[`設計書.md`](設計書.md) §7.2 でリアルタイム手段を選定することになり、候補は Supabase Realtime、Pusher、短時間のポーリングである。**この場合 NFR-02（0.5秒以内）は未達のリスクを負うので、§9 にリスク項目を追加すること。**

## 6. スパイクが終わったら

通ったなら、[`設計書.md`](設計書.md) §7.2 の空欄を埋める。RSSI の閾値（または送信出力の設定）と、受け渡しの同期手段が確定する。§6 の NFR-02 の「未実測」も更新できる。

落ちたなら、該当する設計の節へ戻る。スパイク1が落ちれば §1.2 と §2、スパイク2なら §2.2 と NFR-03、スパイク3なら §7.2 と §9 である。**落ちた結果を「実装で何とかする」で先送りしない。** 設計に戻ることがこの手順書の目的にあたる。

判断に迷う結果が出た場合は、迷ったまま実装に進まず、[`設計書.md`](設計書.md) §8.2 に従って Issue を立てて論点を残すこと。
