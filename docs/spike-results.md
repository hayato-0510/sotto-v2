### 追加で確認した項目（18:15〜18:35、同じ2台）

| 項目 | 結果 | 備考 |
| :--- | :--- | :--- |
| §4.5 端末A を強制終了 → 開き直す | ○ | 役割選択にも4択にも戻らず「こう受け取っています」＋要約から始まる。**発信は始まっていない**（通知0件、logcat に advertise なし）。AGENTS.md §4 |
| §4 端末B 動作画面で ［やめる］ | ○ | 端末A は「席がほしい、と発信しています」に戻り、端末B は「すぐ近くに…」に戻る |
| §4 端末B を前面から外す（他アプリ・画面オフ） | ○（設計どおり） | スキャンが止まる。戻すと再開。「画面を開いている間だけスキャンする」プル型（設計書 §3.4） |
| §5 混み具合で動作が変わるか | ○ | 同じ需要「立っているのがつらい」に対して下表。**3つとも発話語なし（FR-12）** |

同じ需要に対する混み具合ごとの動作（AI-2）：

| 混み具合 | 生成された動作 | 理由 |
| :--- | :--- | :--- |
| 空いている | 席を立ち席の前で2秒待ち移動する | 3駅の間座って体調を整えるためです |
| 混んでいる | 立ち上がり通路側に寄り席へ案内する | 立っているのが辛いためです |
| ぎゅうぎゅう | 荷物を寄せ、隣との間を空けて座り位置をずらす | 超満員で身動きがとれないためです |

方向は設計どおり分かれた。空いている＝その場を離れる／混んでいる＝案内して残る／
ぎゅうぎゅう＝離れず隣を空ける。ただし「空いている」の理由文（3駅…）は
`stopsToAlight` の値をそのまま述べており、やや不自然。プロンプト調整の余地がある。

## 観測した RSSI（参考値・簡略）

`adb logcat` の `BtGatt.GattService: onScanResult` から。厳密な測定ではない。

| 状況 | Sotto 発信端末の RSSI | 判定閾値 `nearRssiDbm` |
| :--- | :--- | :--- |
| 2台が机の上（数十cm） | 約 -66 dBm | -75（超えている＝「近い」） |
| 5m以上＋壁越し | 閾値未満／検出されず | 同上 |

暫定閾値 -75 dBm は、この2条件を分けるには機能した。ただし 1〜5m の中間や混雑環境は未測定。

## 気づき

- **端末B のタップ座標がずれやすかった。** 画面解像度が端末で違う（S10 1080×2280、A51 1080×2400）ため、
  adb の座標指定は端末ごとに出し直す必要がある。デモ収録では手で操作するので問題にならない
- **端末A で別アプリ（開発ビルドの ObjecTalk）が前面に割り込んだ。** 収録中に起きると撮り直しになる。
  収録前にその端末の他アプリを止めておく
- **権限ダイアログの文言は「相対位置の特定」を含む。** これは Android 12+ の `BLUETOOTH_SCAN` 権限の
  OS 側の定型文で、こちらの `neverForLocation` 指定とは別。位置情報は取得していないが、
  利用者には位置を取るように読める。デモや説明でひとこと補足する余地がある
- **通知権限のダイアログが端末A で出なかった。** Android 12（API 31）では `POST_NOTIFICATIONS` が
  ランタイム権限でないため。Android 13 の端末B では譲る側フローで一度聞かれた
- **周囲の他の BLE 機器が割り込む。** 端末B に、無関係な Polar のフィットネス時計から
  Bluetooth ペアリング要求ダイアログが繰り返し出て、譲る側フローを止めた（Sotto の
  スキャンフィルタは効いており、GATT は正しく端末A へ繋がる。ダイアログは時計アプリ
  `fi.polar.polarflow` の別動作）。**収録前に、周囲のスマートウォッチ等の BLE 機器と
  そのコンパニオンアプリを止めておく**
- **端末B の自動ロックが速い。** ロック＝画面オフでスキャンが止まる（設計どおり）ので、
  収録中は譲る側の端末をスリープさせない設定にしておく
