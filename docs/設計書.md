## 改版履歴

v2.0 から v3.0 までは、代替案比較の深掘り、リスクの洗い出し、要求と要件と設計の層の分離を順に進めてきた（旧版の履歴は git 履歴を参照）。

v3.0 から v4.0 での変更は、それまでの改版とは性質が違う。**前提を2つ捨てた。**

第一に、Web アプリという前提を捨てた。v3.0 は「ブラウザでは近接検知が原理的に不可能」という制約を出発点に、GPS と号車番号の自己申告で代用する方向を組み立てていた。しかしこの制約は Web に限った話であり、ネイティブアプリなら近接検知は実証済みの技術である。開発チームが iOS / Android のどちらも作れると確認できたため、制約自体を外した。

第二に、緑色に発光して席の前に立ちはだかる受け渡し方式を捨てた。v3.0 §2.8 は代替案を横に並べた末に「消去法でこれしかない」と結論しつつ、同じ節で「サポーターが恥ずかしがらずにやってくれるかは未検証」と認めていた。マッチングを隣接した人同士に限ると、この方式が担っていた横取り防止と位置特定の両方が不要になる。前提が変われば消去法の答えも変わる。

これに伴い、v3.0 の §2.3（GPS＋号車番号）・§2.4（固定デモ車両）・§2.7（Pusher 選定）・§8.1〜8.4（npm と LAN 経由の実機確認手順）は無効になった。本書からは削除してある。

## 0. この文書の位置づけ

## 1. 接続方式：近接検知（全面設計し直し）

### 1.1 何が問題だったか

Sotto の核心は、見知らぬ乗客同士が一言も交わさず、目線も合わせずに繋がることにある。合言葉方式はその合言葉自体を誰かが誰かに伝える必要があり、見知らぬ他人同士では伝達手段がない時点で成立しない。無言以前に非対面の時点で詰む。

v3.0 はこの反省を踏まえて合言葉を廃止したが、代わりに置いた「号車番号の自己申告＋GPS 概略位置」にも別の問題があった。混雑した車内で体調の悪い人が今何号車かを見上げるのは現実的ではなく、慢性的に必要な利用者は設定を維持しない。加えて GPS は地下区間で精度が落ちる。

### 1.2 設計方針は2つ

**識別子は使ってよい。ただし生成も伝達も交換もすべてシステムが行い、利用者は一度もそれを読み上げず、入力せず、見せ合わない。** これは v3.0 から引き継ぐ。要件定義書 FR-01 が禁じているのは利用者に識別子を運ばせることであって、内部で識別子を使うことではない。

**マッチングは隣接した人同士に限る。** これが v4.0 の新しい軸である。数m以内の相手としか繋がないことで、車内を横断する移動と席を長時間確保する動作の両方が不要になる。当初これは技術的な割り切りとして出てきた案だったが、近接検知を導入した以上は積極的な設計意図として扱う。

### 1.3 Web を捨ててネイティブにした判断

| 観点 | Web（PWA を含む） | ネイティブ（iOS / Android） |
| :--- | :--- | :--- |
| 近接検知 | **不可能**。周囲の端末を無許可でスキャンする API がなく、自らを BLE の peripheral として広告する手段もない。Chrome / Edge / Safari / Firefox のいずれも同じ（2026年時点で確認済み） | **可能**。CoreBluetooth と Android の BLE で実証済み。AirTag や接触確認アプリと同じ原理 |
| バックグラウンド動作 | 弱い。ページを閉じるとスキャンも待機も止まる | 制約はあるが可能。FR-15 の受動サインが成立する |
| 配布 | URL を開くだけ | インストールが必要 |
| 開発コスト | 低い | 高い。iOS の実機ビルドに Mac と Apple Developer 登録が要る |

判断は近接検知の1点で決まった。FR-14 が満たせなければ隣接限定という設計の土台が崩れ、その上に乗っている FR-05・FR-08 廃止・FR-15 がすべて成立しなくなる。配布と開発コストの不利は、デモ動画の撮影であれば TestFlight やサイドロードで吸収できる。

**この判断が成立する条件は、開発チームが実際にネイティブアプリを作れることである。** 前身は開発期限が24時間しかないという理由でネイティブ化を見送っていた。今回はチームの体制を確認した上で選んでいる。前提が変わったので結論も変わった。

### 1.4 近接検知の設計

受け手と譲る側の**双方が発信し、双方がスキャンする。**

片方だけを発信側にする案も検討した。機微なのは需要の側なので、譲る側だけが発信し、受け手はスキャンに専念すれば露出を避けられる。しかしこれは受け手にバックグラウンドスキャンを常時回させることになり、譲る側がアプリを開いたその瞬間に判定するという体験（§2.2）も崩れる。

双方向にした上で、露出そのものを次の4点で抑える。

**識別子を定期的に更新する。** 固定のトークンを出し続けると同じ端末を時空間で追跡できてしまう。15分程度で更新し、サーバは解決できるが外部の観測者は更新前後を紐付けられない形にする。接触確認アプリで実績のある手法であり、iOS は BLE の MAC アドレスも既定でランダム化する。

**発信は電車の移動を検知している間だけに限る。** 常時設定は意思の表明であって、24時間の発信ではない。端末が電車らしい動きを感知したときだけ実際に電波を出す。利用者には見えない挙動で、露出する時間が大幅に縮む。

**ペイロードを最小にする。** 電波に載せるのは「需要モードの利用者がここにいる」という事実とトークンだけとする。何が必要かという中身はサーバ側に置き、マッチした譲る側にだけ抽象化して渡す（[`AGENTS.md`](../AGENTS.md) §3）。

**発信中であることを常に画面に示し、ワンタップで止められるようにする。** 隠れて発信しない。

残るリスクは、利用者が少ない時期に需要ビーコンが目立つことである。これは上記のどれでも解決しない（§9）。

### 1.5 却下した代替案

| 案 | 却下理由 |
| :--- | :--- |
| GPS 概略位置＋号車番号の自己申告（v3.0 の案） | 号車番号を覚えている人が少ない。慢性利用者は設定を維持しない。地下区間で GPS の精度が落ちる |
| 号車ごとの QR コード掲示 | 鉄道事業者の掲出協力が前提で、自走できない |
| 加速度・停車リズムの相関で同じ電車を判定 | 「同じ電車」までは取れるが車内で端から端は分けられない。隣接限定という設計方針に届かない |
| 超音波によるデータ通信 | Web に留まる場合の唯一の近接検知手段として検討したが、ネイティブを選んだ時点で BLE より不利になった。マイク権限の心理的コストも大きい |
| 専用ビーコン機器の設置 | 追加ハードウェアはスコープ外（要件定義書 §3）。近接検知が端末内蔵の無線で足りるため、必要性そのものが消えた |

## 2. 体験の設計

### 2.1 プロダクトの性格：行為重視、締めるのは混雑時だけ

特定の1対1のマッチを確実に成立させることよりも、**立ち上がって席を渡すという行為のハードルを下げること**を主目的に置く。1対1で繋がったかどうかは二次的である。譲る側が自分の意思で動く体験（§2.2）とも、固まってしまう人を主役に置いた要求（要求定義書 §2）とも、この置き方が噛み合う。

ただし横取りを無視はできない。善意が実らない構造は要求定義書 §1 で述べた課題そのものであり、成功指標は「席を必要とする人が座れた」に置いたままにする。

そこで**混雑度をダイヤルとして使う。**

空いている場合とやや混雑している場合は、行為重視で通す。譲る側は立って、そのまま離れてよい。待つ状態が発生しないので、成立したかどうかを気にする局面自体がない。確認もタイムアウトも要らない。

混雑している場合と超満員の場合は、マッチングを締める。AI が返す動作が「座面に手を添えたまま、相手が座るまで待つ」に変わり、受け手の画面にも席の在処がはっきり出る。ここは横取りが現実の脅威であり、受け渡しの失敗が全体の失敗に直結する。

この分岐には副産物が2つある。共通ケースのフローが軽くなること。そして混雑度によって挙動が正反対になること自体が、AI-2 の必然性を示す材料になることである。

### 2.2 起点：プル型

譲る側に push 通知で割り込まない。**譲る側が自分でアプリを開いて動く。**

電車内で「声をかけようか」と葛藤している人は、すでに周囲を見ている。その瞬間にアプリが応えるほうが、無関係なタイミングで通知が鳴るより自然である。通知不安が生じず、行動が完全に自己起点になるので、固まってしまう人を主役に置いた設計と噛み合う。ネイティブにした結果 push は技術的に可能になったが、**プル型は意図して維持する。**

純粋なプル型だけでは、譲る側がアプリを開かない限りマッチが起きない。そこで受動サイン（FR-15）を1つだけ許す。音も振動も画面の点灯もない静かな通知とアイコンのバッジで、次に端末を見たときに気づく程度に留める。1回の遭遇につき1回だけ出し、無視されても催促しない。トリガーは「着席して5分以上経過し、かつ近くに需要がある」とする。座ったばかりの人を急かさず、混雑路線でノイズ化することも防げる。

受け手の画面は、実際の申し出が届くまで暗いままにする。「助けられる人が近くに3人います」と表示して誰も譲らなかった場合、それは残酷なだけである。

### 2.3 受け渡し：発光もナビもしない

譲る側が［ 譲る ］を押すと、受け手の画面に「ごく近くの人が席を空けます」と出る。特定の人物を指し示す表示は出さない。近接検知が隣接を保証しているので、譲る側が立ち上がるのを目視で捉えれば足りる。

最後の数mは人間の目が閉じる。日常でも隣の人が立ち上がれば気づく。アプリの仕事は、その瞬間に受け手を正しい方向へ向けさせることだけである。混雑時は AI が返す「座面に手を添える」という動作が、そのまま控えめな目印を兼ねる。掲げて見せるビーコンとは違う。

目視で見つけられなかった場合は、受け手が［ 見つからない ］を押す。その場合は「相手が見つけられないようです。少し目印を出しますか」と譲る側に尋ね、**任意で**15秒だけマークを表示する。無発光を既定に保ちつつ、駄目なときだけ譲る側の選択で段階を上げる。それでも成立しなければ解放して再マッチへ戻す。

### 2.4 見送り：概念がほぼ消えた

プル型では、譲る側は自分でアプリを開いたからプロンプトを見る。見た上での分岐は3つある。

**譲らずに閉じる。** これが主たる経路である。押さずに閉じるのは単なる非アクションであり、何も起こらない。受け手はこの人が見たことすら知らない。コストがゼロで完全に不可視な「ノー」が、機能を1つも足さずに成立している。辞退ボタンは設けない（FR-09）。

**［ 譲る ］を押した後に取り消す。** 囲まれていた、降車駅だった、また固まった、はいずれも起こる。確認を挟まず理由も聞かず、席へ戻ってよいと明示して探索状態に戻す（FR-17）。

**取り消した時点で受け手が既に画面を見ている。** この場合は受け手側の表示をそっと引っ込める。「その人は無理でした」ではなく「まだ探していますね」と出す。

v3.0 にあった「辞退したサポーターを除外して次の候補へ即リレーする」機構は不要になった。push で打診した候補の列がもう存在しないためである。取り消されたら受け手の需要が発信中に戻り、次にアプリを開いて［ 譲る ］を押した人が拾う。通常フローの再開にすぎない。

無痛の原則は維持されている。受け手は「誰かが助けを考えて、やめた」という痛みを一度も感じない。

### 2.5 お礼

受け手が着席後に［ ありがとう ］を1タップすると、譲る側の画面に「そっと伝わりました」と出る。文字によるメッセージ入力は設けず、往復も作らない（FR-06）。

これは装飾ではない。目線も合わせない体験にすると、受け渡しの瞬間に社会的な負債が宙に浮く。受け手は礼を欠いたと感じ、譲る側は見てもらえなかったと感じ、どちらかが耐えきれず会釈する。お礼のタップがその負債を吸収するので、両者が会釈から解放される。

機能的なクローズも兼ねる。このタップで両端末がリセットされる。一定時間タップがない場合は受け手側に「座れましたか」と出し、座れなかった場合は再マッチへ回す（FR-10）。混雑ブランチに限り、譲る側にも「うまくいかなかったかもしれません。座り直しても大丈夫です」を出す。譲った席にこだわらせないための逃げ道である。

### 2.6 排他制御

**複数の譲る側がほぼ同時に［ 譲る ］を押した場合**、状態遷移を認めるのは先着1件のみとする。2件目には「他の方が席を譲りました。ありがとうございます」と返す。冷たく断らない。

**近くに受け手が複数いる場合**、譲る側に選ばせない。選ぶという行為は判断であり、判断を消したという本作の中核が崩れる。システムが待ち時間の長い順に1人へ割り当て、もう1人は待機を継続する。

**常時設定の受け手がすでに座っている場合**（設定が古くなっているケース）、譲る側の申し出を受ける前に受け手へ「今、席は必要ですか」を確認する（FR-18）。不要なら譲る側に「相手はもう大丈夫でした」と返して解放する。

## 3. 画面構成と状態遷移

### 3.1 画面一覧

| 画面 | 役割 | 対応要件 |
| :--- | :--- | :--- |
| 起動・役割選択 | 「席が必要」「座席にいる（譲れる）」を選ぶ | FR-02 |
| 需要の宣言（受け手・一時） | 自由記述と状態の選択。Needs 確認へ | FR-03, FR-16 |
| Needs 確認（受け手） | ステップ1の結果を本人だけに見せ、確認して発信を始める | POSTMORTEM の確認フローを踏襲 |
| 常時設定（受け手・慢性） | 一度の設定で継続。発信中の表示と停止 | FR-16, NFR-03 |
| 待機（受け手） | ほぼ無表示。申し出が届くまで暗いまま | §2.2 |
| 申し出の受信（受け手） | 「ごく近くの人が席を空けます」。見つからない／座れなかった | FR-05, FR-10 |
| 必要確認（受け手・慢性のみ） | 「今、席は必要ですか」 | FR-18 |
| お礼（受け手） | ワンタップ送信 | FR-06 |
| 需要の提示（譲る側） | 「すぐ近くに席を必要としている人がいます」＋混み具合の1タップ＋［ 譲る ］ | FR-04, FR-07 |
| 動作の提示（譲る側） | AI が生成した身体動作と理由。取り消し | FR-07, FR-17 |
| 混雑度対比（審査用） | 混雑度で動作がどう変わるかを並べて見せる | FR-13 |

混雑度対比の画面は審査員向けの説明ツールであり、受け手と譲る側のどちらの本編フローにも登場させない（POSTMORTEM 根本原因4：デモ操作と製品画面の分離）。

FR-13 はライブ生成にせず、事前に生成した複数パターンを静的に並べる。撮影中にレート制限へ当たるリスクを負う価値がない。

### 3.2 状態遷移（1件の需要のライフサイクル）

```
advertising（発信中。電車の移動を検知している間のみ）
  → offered（いずれかの譲る側が［ 譲る ］を押した）
    → confirming（慢性設定のみ：受け手へ「今、必要ですか」）
        → advertising（不要だった場合。譲る側へは「もう大丈夫でした」）
        → handing_over
    → handing_over（動作を提示し、受け渡し中）
      → completed（お礼の送信で終了）
      → advertising（取り消し・見つからない・座れなかった。いずれも受け手には理由を出さない）
```

譲らずに閉じた場合はこの図に現れない。状態が動かないからである。ここが v3.0 の `declined_relay` との最大の違いにあたる。

## 4. データモデル

`lib/types.ts` の `Condition` / `Needs` / `Situation` / `Handoff` は移植済みのものをそのまま使う。v3.0 が新規に定義していた `Request` と `SupporterPresence` は、名前と中身の両方を見直す。

疾患名・障害名・氏名・顔写真はいずれの型にも持たせない（[`AGENTS.md`](../AGENTS.md) §3、NFR-03）。位置情報も型に持たせない。

具体的な型定義は、言語とプラットフォームが決まっていないため §7 の技術選定パスに回す。現時点で確定しているのは、保持すべき情報が次の4つに限られることである。

需要そのもの（Needs と Situation、状態、生成された Handoff）。近接検知に使う更新される識別子と、それを解決するための内部キー。待ち時間の長い順に割り当てるための発生時刻。そして受け渡しの成否。

いずれも受け渡しの完了時に破棄する。永続化する理由がない。

## 5. AI設計思想

要求定義書 §4 の AI-1 / AI-2 / AI-3 を、既存の2段階パイプラインへ対応させる。プロンプト（`lib/prompts.ts`）は前身で実運用のうえ3回チューニング済みのため変更しない（POSTMORTEM「使える部分」）。設計として明示すべきなのは、なぜ2段階に分けたかである。

ステップ1（`extractNeeds`）を乗車前の1回に限定するのは、自由記述の解読が乗車中に何度も要る処理ではないからだ。乗車後に都度呼べば応答速度が悪化するだけで、同じ入力から違う結果を得る理由がない。

ステップ2（`generateHandoff`）を［ 譲る ］が押される都度呼ぶのは、混雑度に応じた動作生成がその時の車内状況に依存し、Needs だけでは決まらないためである。混雑度は乗車前には分からない。

v4.0 では、混雑度を報告するのが受け手から譲る側に変わった（FR-04）。ステップ2の呼び出しタイミングが「受け手が要請を出した瞬間」から「譲る側が譲ると決めた瞬間」へ移る。入出力の形は変わらない。

AI-3（語気の調律）はステップ2の出力に埋め込み、別のモデル呼び出しにはしない。語気だけを独立させても追加のレイテンシに見合わない。

**却下した代替案**：ステップ1と2を1回の呼び出しに統合する案も検討した。しかし乗車前の落ち着いた入力と、車内の混雑度という動的な情報を同じプロンプトに混ぜると、混雑度が変わるたびに自由記述の解釈まで再生成させることになる。レイテンシが伸び、本人が確認済みの Needs が揺れうる。NFR-01 と確認フローの両方に反するため却下した。

### 5.1 安全設計

`containsSpeech`（`lib/speech.ts`）による発話検出とフォールバック（`lib/fallback.ts`）はそのまま使う。FR-12 はこの仕組みの要求定義であり、実装は既に要求を満たしている。

AI の非目標（診断をしない、発話を出力しない、危険動作を出力しない）は `lib/prompts.ts` に反映済みで、設計変更は不要である。

ネイティブアプリになっても**API キーはクライアントに置かない。** 生成はサーバ側で行い、アプリはそのエンドポイントを叩く。ネイティブのバイナリは解析可能であり、Web より安全にはならない（[`AGENTS.md`](../AGENTS.md) §1）。

## 7. 技術選定パス（未着手）

**この節は空欄である。** 体験の設計が固まった段階で本書を書いているため、実装技術は何も決まっていない。決めるべき項目だけを挙げておく。

**プラットフォームと言語**。ネイティブ（Swift と Kotlin の2本）、Flutter、React Native のいずれか。判断軸は BLE の peripheral 役への対応状況、チームの習熟、iOS ビルド環境である。前身の検討では `react-native-ble-plx` が peripheral をサポートしていない点が壁になったが、これは React Native 固有の事情であり、他の選択肢では変わる。

**BLE の実装方式**。サービス UUID の設計、更新される識別子の生成と解決、RSSI から距離を推定する際の閾値を決める必要がある。最も読みにくいのはバックグラウンドでの発信とスキャンの挙動で、iOS と Android で挙動が大きく違う（§9-5）。

**受け渡しウィンドウの同期手段**。NFR-02 を満たす必要があるのはこの数十秒だけになった。常時接続を張るのか、その都度の通信で足りるのかから決める。

**AI サーバの持ち方**。既存の `lib/*.ts` は Node 前提で書かれている。これをそのままサーバとして残すか、別の形にするか。

**電車の移動の検知方法**（モーションゲート、§1.4）。加速度センサーの利用と、権限の要求タイミング。

決める前に**近接検知のスパイクを先に行う。** 2端末で、混雑した車内やポケットの中でも数m以内という判定が安定して出せるかを実測する。ここが駄目なら隣接限定という設計の土台が崩れ、本書の §1 と §2 を書き直すことになる。前身の失敗は、この種の検証を「もう決まったこと」として飛ばした点にあった。

## 8. 開発フロー

### 8.1 git 運用

[`AGENTS.md`](../AGENTS.md) の git 規則をそのまま適用し、次の順序を徹底する。

実装前に関連する既存コードと POSTMORTEM の該当箇所を読む。実装は意味のある変更1つに絞り、混ぜない。検証を通してからコミットする（通らないコードはコミットしない）。デバッグして直した場合は、試行錯誤の途中経過をコミットせず、最終的に通った状態のみを1コミットにまとめる。コミット時はパスを明示し（`-A` と `.` は使わない）、メッセージには何をしたかではなくなぜそうしたかを書く。

`git reset --hard` / `git clean` / `git restore` は使わない。必要な場面が来たら実行前に確認を取る。

通常の実装は `main` に直接コミットしてよい。動作しなくなるリスクのある大きな変更は作業用ブランチを切り、検証が通ってから `main` にマージする。

### 8.2 Issue 駆動とバージョン管理

タスクは着手前に GitHub Issue を立てる。§7 の各項目、§9 のリスク項目、§10.3 のギャップ項目は、着手時にそのまま1 Issue に対応させる。Issue 本文には対応する本書の節番号を必ず書き、後から「なぜこの実装か」を設計へ遡って追えるようにする。

コミットメッセージには Issue 番号を含める。ラベルは最低限 `bug`（動いていたものが壊れた）、`design-gap`（要求定義書にない設計判断）、`spike`（§7 の未検証項目）の3種を使う。

マイルストーンはフェーズに合わせて切る。デモ直前には動作確認済みのコミットへタグを打ち、締切直前の変更で壊れた場合に戻れる基点を残す。

### 8.3 テスト方針

`lib/*.test.ts`（vitest）の `speech.test.ts` と `fallback.test.ts` はそのまま維持する。プロダクトの安全根幹にあたり、接続方式の変更と無関係である。

実機2台での通し確認は自動化しない。撮影に使う回線環境や実機に依存するテストは再現性が低く、保守コストに見合わない。手動チェックリストとして別途まとめる。

## 9. リスク

提出物は録画されたデモ動画であり、審査員の前でのライブ実演ではない。会場の通信環境やタイミングといったライブ実演固有のリスクは、撮り直しで解決するためここに含めない。残すのは**撮り直しでは解決しないもの**だけである。

| # | シナリオ | 影響 | 対策 |
| :---: | :--- | :--- | :--- |
| 1 | 近接検知が実機で安定しない（混雑時、ポケット内、RSSI の揺れ） | 隣接限定という設計の土台が崩れ、§1・§2 の書き直しになる | §7 のスパイクを実装より先に行う。**本書で最も重いリスク** |
| 2 | 混雑時の「座面に手を添えて待つ」に心理的抵抗があり、機能してもやりたくない動作になる | 撮影はできても、実運用と審査で「本当に人がこれをするか」を突かれる | 実機確認に、動作の成否だけでなく譲る側の心理的抵抗を聞く項目を加える。抵抗が大きければ混雑ブランチの動作を再設計する |
| 3 | 利用者が少ない時期、需要を発信している端末が周囲に1台しかなく、その発信自体が目立つ | 受け手の脆弱性が露出する | §1.4 の対策では解決しない。**未解決として記録する** |
| 4 | 撮影中に Gemini の無料枠のレート制限へ当たる | AI 生成が失敗しフォールバック文になり、AI が動いていないように見える映像になる | `isFallback` フラグを画面に必ず明示して隠さない。撮影直前にウォームアップし、リハーサルで挙動を把握してから本番テイクを撮る |
| 5 | iOS のバックグラウンドでの BLE 発信・スキャンの制約により、受動サイン（FR-15）が期待通り働かない | プル型の弱点（アプリを開かないとマッチしない）を補う手段が失われる | §7 で挙動を確認する。駄目なら受動サインを諦め、純プル型に縮退させる（体験の土台は崩れない） |
| 6 | App Store の審査で、バックグラウンドの BLE 利用の正当性を問われる | 配布が止まる。ただしデモ動画の撮影は TestFlight で可能 | モーションゲートと発信中の明示（§1.4）が、そのまま審査への説明材料になる |
