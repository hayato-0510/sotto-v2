## 改版履歴

v2.0 から v3.0 までは、代替案比較の深掘り、リスクの洗い出し、要求と要件と設計の層の分離を順に進めてきた（旧版の履歴は git 履歴を参照）。

v3.0 から v4.0 での変更は、それまでの改版とは性質が違う。**前提を2つ捨てた。**

第一に、Web アプリという前提を捨てた。v3.0 は「ブラウザでは近接検知が原理的に不可能」という制約を出発点に、GPS と号車番号の自己申告で代用する方向を組み立てていた。しかしこの制約は Web に限った話であり、ネイティブアプリなら近接検知は実証済みの技術である。開発チームが iOS / Android のどちらも作れると確認できたため、制約自体を外した。

第二に、緑色に発光して席の前に立ちはだかる受け渡し方式を捨てた。v3.0 §2.8 は代替案を横に並べた末に「消去法でこれしかない」と結論しつつ、同じ節で「サポーターが恥ずかしがらずにやってくれるかは未検証」と認めていた。マッチングを隣接した人同士に限ると、この方式が担っていた横取り防止と位置特定の両方が不要になる。前提が変われば消去法の答えも変わる。

これに伴い、v3.0 の §2.3（GPS＋号車番号）・§2.4（固定デモ車両）・§2.7（Pusher 選定）・§8.1〜8.4（npm と LAN 経由の実機確認手順）は無効になった。本書からは削除してある。

**v4.1 では、ネイティブへ移った後の制約を調べ直した。** iOS が背景で発信したサービス UUID は Apple 独自の overflow area に入り、Android からは検出できない。また iOS の背景スキャンは信頼できる peer-to-peer 検知に使えない。前者から「当面は同一OS間に限る」という割り切りを、後者から FR-15（受動サイン）の廃止を導いた（§1.5）。**ネイティブにすれば近接検知の問題が全部消えると考えていたのは楽観だった。** 消えたのは「原理的に不可能」の部分だけで、背景での挙動には別の壁がある。

## 0. この文書の位置づけ

文書の連鎖は、コンセプト（1文）→ [`要求定義書.md`](要求定義書.md)（なぜ）→ [`要件定義書.md`](要件定義書.md)（何を）→ 本書（どう作るか）→ [`作品概要書.md`](作品概要書.md)（対外要約）である。本書は要件定義書の各要件を満たす設計だけを扱い、なぜその要件が要るかは要件定義書へ、なぜそのミッションかは要求定義書へ遡る。

前身リポジトリはこの段階で「近接検知はブラウザで実装不可能。デモでは合言葉で代用する」と書き、そのまま実装まで進んだ。合言葉の手渡しが「見知らぬ他人同士」という前提と矛盾することに気づいたのは、実装が終わってからだった（[POSTMORTEM.md](POSTMORTEM.md) 根本原因1・3）。

同じ構造の失敗を防ぐため、本書では**未検証の項目を空欄のまま残す**方針を取る。埋まっていない節があるのは書き漏らしではなく、まだ決めていないことを決めたふりにしないためである。

## 1. 接続方式：近接検知（全面設計し直し）

### 1.1 何が問題だったか

Sotto の核心は、見知らぬ乗客同士が一言も交わさず、目線も合わせずに繋がることにある。合言葉方式はその合言葉自体を誰かが誰かに伝える必要があり、見知らぬ他人同士では伝達手段がない時点で成立しない。無言以前に非対面の時点で詰む。

v3.0 はこの反省を踏まえて合言葉を廃止したが、代わりに置いた「号車番号の自己申告＋GPS 概略位置」にも別の問題があった。混雑した車内で体調の悪い人が今何号車かを見上げるとは考えにくい。慢性的に必要な利用者は設定を維持しない。加えて GPS は地下区間で精度が落ちる。

### 1.2 設計方針は2つ

**識別子は使ってよい。ただし生成も伝達も交換もすべてシステムが行い、利用者は一度もそれを読み上げず、入力せず、見せ合わない。** これは v3.0 から引き継ぐ。要件定義書 FR-01 が禁じているのは利用者に識別子を運ばせることであって、内部で識別子を使うことではない。

**マッチングは隣接した人同士に限る。** これが v4.0 の新しい軸である。数m以内の相手としか繋がないことで、車内を横断する移動と席を長時間確保する動作の両方が不要になる。当初これは技術的な割り切りとして出てきた案だったが、近接検知を導入した以上は積極的な設計意図として扱う。

### 1.3 Web を捨ててネイティブにした判断

| 観点 | Web（PWA を含む） | ネイティブ（iOS / Android） |
| :--- | :--- | :--- |
| 近接検知 | **不可能**。周囲の端末を無許可でスキャンする API がなく、自らを BLE の peripheral として広告する手段もない。Chrome / Edge / Safari / Firefox のいずれも同じ（2026年時点で確認済み） | **可能**。CoreBluetooth と Android の BLE で実証済み。AirTag や接触確認アプリと同じ原理 |
| バックグラウンド動作 | 弱い。ページを閉じるとスキャンも待機も止まる | 発信は可能。**スキャンは不可に近い**（§1.5） |
| 配布 | URL を開くだけ | インストールが必要 |
| 開発コスト | 低い | 高い。iOS の実機ビルドに Mac と Apple Developer 登録が要る |

判断は近接検知の1点で決まった。FR-14 が満たせなければ隣接限定という設計の土台が崩れ、その上に乗っている FR-05 と FR-08 の廃止も成立しなくなる。配布と開発コストの不利は、デモ動画の撮影であれば TestFlight やサイドロードで吸収できる。

**ただしネイティブにしても制約がなくなるわけではない。** 背景での挙動には iOS 固有の壁があり、それが §1.5 で扱う制約と FR-15 の廃止につながった。

**この判断が成立する条件は、開発チームが実際にネイティブアプリを作れることである。** 前身は開発期限が24時間しかないという理由でネイティブ化を見送っていた。今回はチームの体制を確認した上で選んでいる。前提が変わったので結論も変わった。

### 1.4 近接検知の設計

受け手と譲る側の**双方が発信し、双方がスキャンする。**

片方だけを発信側にする案も検討した。機微なのは需要の側なので、譲る側だけが発信し、受け手はスキャンに専念すれば露出を避けられる。しかしこれは受け手にバックグラウンドスキャンを常時回させることになり、譲る側がアプリを開いたその瞬間に判定するという体験（§2.2）も崩れる。

双方向にした上で、露出そのものを次の4点で抑える。

**識別子を定期的に更新する。** 固定のトークンを出し続けると同じ端末を時空間で追跡できてしまう。15分程度で更新し、サーバは解決できるが外部の観測者は更新前後を紐付けられない形にする。接触確認アプリで実績のある手法であり、iOS は BLE の MAC アドレスも既定でランダム化する。

**発信は電車の移動を検知している間だけに限る。** 常時設定は意思の表明であって、24時間の発信ではない。端末が電車らしい動きを感知したときだけ実際に電波を出す。利用者には見えない挙動で、露出する時間が大幅に縮む。

**ペイロードを最小にする。** 電波に載せるのは「需要モードの利用者がここにいる」という事実とトークンだけとする。何が必要かという中身はサーバ側に置き、マッチした譲る側にだけ抽象化して渡す（[`AGENTS.md`](../AGENTS.md) §3）。

**発信中であることを常に画面に示し、ワンタップで止められるようにする。** 隠れて発信しない。

残るリスクは、利用者が少ない時期に需要ビーコンが目立つことである。これは上記のどれでも解決しない（§9）。

### 1.5 iOS の背景 BLE の制約と、そこから来る2つの割り切り

ネイティブを選んだ後に調べて分かった制約が2つある。**どちらも設計を変えた。**

#### 1.5.1 iOS が背景で発信したものは、Android から見えない

iOS アプリが背景に回ると、サービス UUID は通常のアドバタイズパケットから消え、Apple 独自の「overflow area」へ移る。これは**ブルームフィルタ状のビットマスクで、UUID からビット位置への変換に非公開のハッシュが使われている。** iOS 同士であればサービス UUID を明示指定してスキャンすれば読めるが、Android の標準的なスキャン（サービス UUID でのフィルタ）では、パケットにその UUID が存在しないため検出できない。

形式は逆解析されているので、Apple のメーカーデータを読んでビット位置を直接見れば理論上は可能である。ただし未文書であり、ブルームフィルタなので衝突による誤検出があり、iOS の更新で壊れうる。**コンテスト提出物の中核に置ける代物ではない。**

受け手はスマホをポケットに入れる（＝背景）前提なので、影響はこう出る。

| 受け手（発信） | 譲る側（前景でスキャン） | 結果 |
| :--- | :--- | :--- |
| iOS 前景 | iOS / Android | ○ |
| iOS 背景 | iOS | ○（overflow を読める） |
| **iOS 背景** | **Android** | **✕** |
| Android 背景 | iOS / Android | ○ |

**割り切り：当面のマッチング動作保証を同一OS間（iOS↔iOS、Android↔Android）に限る。** iOS と Android の間は、受け手がアプリを前景に保っている場合にのみ成立する。

この割り切りは[`AGENTS.md`](../AGENTS.md) §5 の対象になる。コードコメントで済ませず、**UIのコピーに「現在は同じ種類のスマホ同士でのみ動作します」と明示すること。** POSTMORTEM 根本原因1は、まさに「デモだから」という理由で簡略化を書いたまま検証を止めたことだった。同じ轍を踏まないために画面へ出す。

審査で「なぜ解決できないのか」を問われた場合の答えは用意できている。**接触確認アプリが OS レベルの専用 API（Exposure Notification）として提供されたのは、この制約をアプリレベルでは越えられないからである。** 各国の初期の独自実装が iOS の背景 BLE でつまずき、Apple と Google の API へ乗り換えた経緯がある。これはこちらの実装力の不足ではなく、Apple の設計判断に由来する壁である。

#### 1.5.2 iOS の背景スキャンは信頼できない。だから FR-15 を廃止した

スキャン側の制約はさらに厳しい。背景に回ると走査の間隔が疎で予測不能になり、1デバイスにつき単発の通知しか届かない。背景では peer-to-peer の近接検知を維持し続けられない。

受動サイン（FR-15）はこれを必要としていたので、**廃止した。** Android では実現しうるが、「Android なら気づけるが iPhone では気づけない」というプラットフォーム差は体験の説明を壊す。プル型（§2.2）に一本化する。

廃止には副作用として利点がある。**背景でのスキャンが要件から消え、残るのは受け手の背景での発信だけになった。** iOS の `UIBackgroundModes` に要るのは `bluetooth-peripheral` の1つだけで、`bluetooth-central` は不要になる。実装の難所が片側に寄り、App Store 審査で正当性を説明すべき背景モードも1つに減る。

### 1.6 却下した代替案

| 案 | 却下理由 |
| :--- | :--- |
| GPS 概略位置＋号車番号の自己申告（v3.0 の案） | 号車番号を覚えている人が少ない。慢性利用者は設定を維持しない。地下区間で GPS の精度が落ちる |
| 号車ごとの QR コード掲示 | 鉄道事業者の掲出協力が前提で、自走できない |
| 加速度・停車リズムの相関で同じ電車を判定 | 「同じ電車」までは取れるが車内で端から端は分けられない。隣接限定という設計方針に届かない |
| 超音波によるデータ通信 | Web に留まる場合の唯一の近接検知手段として検討したが、ネイティブを選んだ時点で BLE より不利になった。マイク権限の心理的コストも大きい |
| 専用ビーコン機器の設置 | 追加ハードウェアはスコープ外（要件定義書 §3）。近接検知が端末内蔵の無線で足りるため、必要性そのものが消えた |

## 2. 体験の設計

### 2.1 プロダクトの性格：行為重視、締めるのは混雑時だけ

特定の1対1のマッチを確実に成立させることよりも、**立ち上がって席を渡すという行為のハードルを下げること**を主目的に置く。1対1で繋がったかどうかは二次的である。譲る側が自分の意思で動く体験（§2.2）とも、固まってしまう人を主役に置いた要求（要求定義書 §2）とも、この置き方が噛み合う。

ただし横取りを無視はできない。善意が実らない構造は要求定義書 §1 で述べた課題そのものであり、成功指標は「席を必要とする人が座れた」に置いたままにする。

そこで**混雑度をダイヤルとして使う。**

空いている場合とやや混雑している場合は、行為重視で通す。譲る側は立って、そのまま離れてよい。待つ状態が発生しないので、成立したかどうかを気にする局面自体がない。確認もタイムアウトも要らない。

混雑している場合と超満員の場合は、マッチングを締める。AI が返す動作が「座面に手を添えたまま、相手が座るまで待つ」に変わり、受け手の画面にも席の在処がはっきり出る。ここは横取りが現実の脅威であり、受け渡しの失敗が全体の失敗に直結する。

この分岐には副産物が2つある。共通ケースのフローが軽くなること。そして混雑度によって挙動が正反対になること自体が、AI-2 の必然性を示す材料になることである。

### 2.2 起点：プル型

譲る側に push 通知で割り込まない。**譲る側が自分でアプリを開いて動く。**

電車内で「声をかけようか」と葛藤している人は、すでに周囲を見ている。その瞬間にアプリが応えるほうが、無関係なタイミングで通知が鳴るより自然である。通知不安が生じず、行動が完全に自己起点になるので、固まってしまう人を主役に置いた設計と噛み合う。ネイティブにした結果 push は技術的に可能になったが、**プル型は意図して維持する。**

純粋なプル型だけでは、譲る側がアプリを開かない限りマッチが起きない。v4.0 の途中まではここに受動サイン（FR-15）を1つだけ許していたが、iOS の背景スキャンでは実現できないと分かったため廃止した（§1.5.2）。**譲る側への通知は一切ない。**

発見性は落ちる。しかし行為重視の立場（§2.1）に立てば、アプリを開かなかった人はその回の譲り手ではない、で筋が通る。むしろ通知が一切ないことは「割り込まない」という原則の徹底として説明しやすく、プロダクト名の「そっと」とも矛盾しない。

受け手の画面は、実際の申し出が届くまで暗いままにする。「助けられる人が近くに3人います」と表示して誰も譲らなかった場合、それは残酷なだけである。

### 2.3 受け渡し：発光もナビもしない

譲る側が［ 譲る ］を押すと、受け手の画面に「ごく近くの人が席を空けます」と出る。特定の人物を指し示す表示は出さない。近接検知が隣接を保証しているので、譲る側が立ち上がるのを目視で捉えれば足りる。

最後の数mは人間の目が閉じる。日常でも隣の人が立ち上がれば気づく。アプリの仕事は、その瞬間に受け手を正しい方向へ向けさせることだけである。混雑時は AI が返す「座面に手を添える」という動作が、そのまま控えめな目印を兼ねる。掲げて見せるビーコンとは違う。

目視で見つけられなかった場合は、受け手が［ 見つからない ］を押す。その場合は「相手が見つけられないようです。少し目印を出しますか」と譲る側に尋ね、**任意で**15秒だけマークを表示する。無発光を既定に保ちつつ、駄目なときだけ譲る側の選択で段階を上げる。それでも成立しなければ解放して再マッチへ戻す。

### 2.4 見送り：概念がほぼ消えた

プル型では、譲る側は自分でアプリを開いたからプロンプトを見る。見た上での分岐は3つある。

**譲らずに閉じる。** これが主たる経路である。押さずに閉じるのは単なる非アクションであり、何も起こらない。受け手はこの人が見たことすら知らない。コストがゼロで完全に不可視な「ノー」が、機能を1つも足さずに成立している。辞退ボタンは設けない（FR-09）。

**［ 譲る ］を押した後に取り消す。** 囲まれていた、降車駅だった、また固まった、はいずれも起こる。確認を挟まず理由も聞かず、席へ戻ってよいと明示して探索状態に戻す（FR-17）。

**取り消した時点で受け手が既に画面を見ている。** この場合は受け手側の表示をそっと引っ込める。「その人は無理でした」ではなく「まだ探していますね」と出す。

v3.0 にあった「辞退したサポーターを除外して次の候補へ即リレーする」機構は不要になった。push で打診した候補の列がもう存在しないためである。取り消されたら受け手の需要が発信中に戻り、次にアプリを開いて［ 譲る ］を押した人が拾う。通常フローの再開にすぎない。

無痛の原則は維持されている。受け手は「誰かが助けを考えて、やめた」という痛みを一度も感じない。

### 2.5 お礼

受け手が着席後に［ ありがとう ］を1タップすると、譲る側の画面に「そっと伝わりました」と出る。文字によるメッセージ入力は設けず、往復も作らない（FR-06）。

これは装飾ではない。目線も合わせない体験にすると、受け渡しの瞬間に社会的な負債が宙に浮く。受け手は礼を欠いたと感じ、譲る側は見てもらえなかったと感じ、どちらかが耐えきれず会釈する。お礼のタップがその負債を吸収するので、両者が会釈から解放される。

機能的なクローズも兼ねる。このタップで両端末がリセットされる。一定時間タップがない場合は受け手側に「座れましたか」と出し、座れなかった場合は再マッチへ回す（FR-10）。混雑ブランチに限り、譲る側にも「うまくいかなかったかもしれません。座り直しても大丈夫です」を出す。譲った席にこだわらせないための逃げ道である。

### 2.6 排他制御

**複数の譲る側がほぼ同時に［ 譲る ］を押した場合**、状態遷移を認めるのは先着1件のみとする。2件目には「他の方が席を譲りました。ありがとうございます」と返す。冷たく断らない。

**近くに受け手が複数いる場合**、譲る側に選ばせない。選ぶという行為は判断であり、判断を消したという本作の中核が崩れる。システムが待ち時間の長い順に1人へ割り当て、もう1人は待機を継続する。

**常時設定の受け手がすでに座っている場合**（設定が古くなっているケース）、譲る側の申し出を受ける前に受け手へ「今、席は必要ですか」を確認する（FR-18）。不要なら譲る側に「相手はもう大丈夫でした」と返して解放する。【このビルドでは発信を毎回本人が始めるため、この確認は置かない。§3.4】

## 3. 画面構成と状態遷移

**UIは様式ではなく引き算のルールで縛る。** 前身は「駅サイン基調のミニマルな意匠」を目指したうえで「濃紺の帯＋同一角丸パネルの反復」に着地し、AIっぽいと指摘された（POSTMORTEM 根本原因5）。同じ言葉で方針を言い直せば同じ場所に着くので、好みの問題として扱わず、構造の禁止事項として定義し直す。

- **カードを使わない。** 角丸パネルもコンテナも置かない。前身の失敗の本体を構造から排除する
- **1画面＝1メッセージ＋最大1アクション。** 情報を2つ並べたくなったら画面を分ける。**唯一の例外として、画面上端に「いまの立場」を常時出す**（次項）

**例外：いまの立場の常時表示（2026-09-10 追加）。** 役割を保存するようにしたため（§3.4）、利用者はいま自分がどちらの側で開いているかを画面から知る必要がある。ところが画面上の他の文はすべて相手のこと（「すぐ近くに、席を必要としている人がいます」）なので、主語の無い「いま座っている」を上に置くと、自分の話か相手の話かが読み取れない。そこで主語を明示して `あなた ／ 席をさがす`・`あなた ／ 席を空ける` とし、姿勢のアイコン（立ち姿・座り姿）と設定への入口を同じ行に置く。1画面1メッセージのルールはこの1行のためだけに緩める。
- **階層は文字サイズだけで作る。** 囲みや背景色で区切らない
- **「何も無い」状態は本当に何も出さない。** 空状態のイラストや説明文を置かない
- **色は状態だけを運ぶ。** 装飾に使わない

このルールなら「同じコンポーネントの機械的な反復」が起こりようがない。反復できるコンポーネントが存在しないからである。加えてこのアプリは9画面の大半が一文とボタン1つしかないため（§3.3）、引き算の側から縛るほうが実態に合う。

### 3.2 状態遷移（1件の需要のライフサイクル）

```
advertising（発信中。電車の移動を検知している間のみ）
  → offered（いずれかの譲る側が［ 譲る ］を押した）
    → confirming（慢性設定のみ：受け手へ「今、必要ですか」）
        → advertising（不要だった場合。譲る側へは「もう大丈夫でした」）
        → handing_over
    → handing_over（動作を提示し、受け渡し中）
      → completed（お礼の送信で終了）
      → advertising（取り消し・見つからない・座れなかった。いずれも受け手には理由を出さない）
```

譲らずに閉じた場合はこの図に現れない。状態が動かないからである。ここが v3.0 の `declined_relay` との最大の違いにあたる。

### 3.3 画面ごとの文言

文言は実装時に書き起こすものではなく、設計の一部として先に確定させる。理由は3つある。発話語が混ざればプロダクトの存在理由が壊れる（FR-12）。疾患情報が譲る側に漏れてはならない（[`AGENTS.md`](../AGENTS.md) §3）。そして固まった人を責める文言はコンセプトの中核を壊す（§2.4）。いずれも実装時の裁量に委ねられる範囲を超えている。

#### 譲る側

**需要の提示**。相手の状態は一切出さない。「近くに必要な人がいる」だけを見せる。これが誤爆をなくす仕組みの、表示上の姿にあたる。

```
すぐ近くに、席を必要としている人がいます

いまの車内は?
［ 空いている ］［ 混んでいる ］［ ぎゅうぎゅう ］

              ［ 譲る ］
```

混み具合の3択は「空いている／混雑／超満員」より口語に寄せた。誰もいないときは「いまは近くにいません」だけを出す。「また見てみてください」は書かない。催促になる。

**動作の提示**。AI の出力（動作・所要秒数・理由）を置く枠であり、［ やめる ］は隅に小さく置く（FR-17）。確認ダイアログを挟まず、理由も聞かない。

```
立って、座面に手を添えたまま。
相手が座るまでそこで待ってください

およそ20秒 ／ ＜理由＞

                          やめる
```

生成が失敗して定型文になった場合は「定型の案内を表示しています」と小さく添える。隠さない（§9-4）。

**お礼が届いた**。「そっと伝わりました」の一行だけを出し、数秒で閉じる。主役への唯一の報酬なので、ここに他の要素を置かない。

#### 受け手

**需要の宣言**。選択肢は体験で書く。「内部疾患」のような診断名は使わず、「見た目には分からない不調」と表現する。

```
どれが近いですか

［ つわり・めまいがある ］
［ 立っているのがつらい ］
［ 足や腰が痛む ］
［ 見た目には分からない不調がある ］

ほかにあれば（100字まで）
例：貧血気味で立っているとふらつく
```

**Needs 確認**。「分析結果」ではなく「こう受け取りました」とする。狙いは訂正を促すことにある。

```
こう受け取りました

＜ステップ1の summary＞

［ これで発信する ］  ［ 書き直す ］
```

**待機**。「近くに3人います」は出さない。誰も譲らなかったときに残酷なだけである（§2.2）。スピナーも進捗も置かない。

```
席がほしい、と発信しています
見つかったら画面が変わります

                        やめる
```

「見つかったら画面が変わります」はスマホをしまってよいと伝えるための一行で、成功を約束していない。モーションゲートで発信が止まっている間は「電車が動きだしたら発信します」に差し替える。

**申し出の受信**。［ ありがとう ］が着席の報告も兼ねる。

```
ごく近くの人が席を空けます
立ち上がる人がいます

［ ありがとう ］      見つからない
```

譲る側が取り消したときは「まだ探していますね」と出す。「その人は無理でした」とは書かない。近くで見つからなかったときは「近くで見つかりませんでした」に［ 待つ ］と［ やめる ］を添える。

#### 起動・役割選択（初回のみ）

```
あなたは、どちらですか

［ 席をさがす ］
［ 席を空ける ］

あとから設定で変えられます

いまは Android どうしでのみつながります
```

「席を譲れる人」とは書かない。善人認定を含意すると善意の搾取に寄る。「譲る／譲られる」も使わない。施す側と施される側を作るからである。両方とも動作で書き、左右を対称にする。「席を空ける」は受け手側の申し出受信画面（「ごく近くの人が席を空けます」）と同じ語で、新しい語を増やしていない。

アプリを開いた時点で、どちらの側も意思があるものとして扱う（席を空けたい人はそのつもりで開き、席が要る人はアプリを入れた時点でそのつもりである）。そのため「〜したい」「〜できる」のような意思を確かめる語は置かない。

（2026-09-10 変更。以前は「席がほしい」「いま座っている」で、毎回この画面を通っていた）

最下部の一行が §1.5.1 の制約を UI に明示する箇所にあたる（[`AGENTS.md`](../AGENTS.md) §5）。「同じ種類のスマホ」では曖昧なので、作る対象を名指しする。

### 3.4 役割と需要の保存（2026-09-10 追加）

席を必要とする人（高齢・妊娠など）も、席を空けたい人も、その立場は乗るたびに変わらない。毎回選ばせるのは、このアプリが消そうとしている手間そのものである。そこで次のように分けた。

| 層 | 保存するか | 理由 |
| :--- | :--- | :--- |
| 役割 | **保存する** | 立場は乗るたびに変わらない。設定で変えるまで維持する |
| 需要の中身（4択・自由記述・要約） | **保存する** | 毎回の4択と AI の待ち（約10秒）を消す。慢性の中身と今日だけの状態（妊娠中で今日はめまいもある等）は区別しない。席が要るという本質は同じだからである |
| 発信 | **保存しない** | 開いただけで発信が始まると「隠れて発信しない」（AGENTS.md §4）に反する。モーションゲートが未実装なので、アプリを開いている間ずっと発信することになる。さらに、その日は座れている人のために誰かが立ち上がる事態が起きうる |

受け手の2回目以降の操作は「開く →［ これで発信する ］」の1タップになる。**この1タップが「いま席が要る」の意思表示を兼ねる**ので、常時設定の必要確認（FR-18）は置かない。

封緘は使い回さず、発信のたびに取り直す。封緘には発生時刻が入っており（`lib/blob.ts`）、待ち時間順の割り当て（§2.6）に使う設計なので、古い封緘を使うとその人が常に最長待機扱いになる。電波に乗るトークンは封緘とは別物で15分ごとに更新されるため、需要を保存しても固定の識別子にはならない。

保存先は本人の端末のアプリ専用領域（`shared_preferences`）だけで、新たに外へ送るものは無い。役割を変えたとき・需要を［ 変える ］で消したときは、いまの流れを畳んで作り直す。畳むときに発信・スキャンが止まる（`mobile/lib/main.dart` の `Home`）。

譲る側の画面が最初の画面になったので、譲る側の［ 閉じる ］は置かない。戻り先が無く、離れ方は端末の操作（ホームへ戻る等）に任せる。「譲らずに閉じる」（§2.4）がボタン無しで成立する。アプリを離れたらスキャンを止め、戻ったら再開する。スキャンするのは画面を開いている間だけ、というプル型（§2.2）を保つためである（`mobile/lib/screens/giver.dart`）。

#### 混雑度対比（審査用）

この画面だけは説明そのものが目的なので、まとまった説明文を許す。

```
同じ状態でも、混み具合で動作が変わります

空いている    混んでいる    ぎゅうぎゅう
＜動作A＞      ＜動作B＞      ＜動作C＞

これは審査用の画面です。製品の導線には現れません
```

#### 実装時の注意

`containsSpeech`（`lib/speech.ts`）は **AI の出力を検証するためのもので、静的な UI コピーには通さない。** 「そっと伝わりました」の「伝わる」が誤検出されうるため、実装側で経路を分けておくこと。

## 4. データモデル

`lib/types.ts` の `Condition` / `Needs` / `Situation` / `Handoff` は移植済みのものをそのまま使う。v3.0 が新規に定義していた `Request` と `SupporterPresence` は、名前と中身の両方を見直す。

疾患名・障害名・氏名・顔写真はいずれの型にも持たせない（[`AGENTS.md`](../AGENTS.md) §3、NFR-03）。位置情報も型に持たせない。

型は2箇所に置かれる。**AIサーバ側は既存の `lib/types.ts`（TypeScript）をそのまま使い、アプリ側は Dart で同じ形を持つ**（§7.1）。同じ定義を2言語で書くことになるが、`Needs` と `Handoff` は AI の入出力契約であって滅多に変わらないため、生成の仕組みを入れるほどではない。**両者がずれたら AI の入出力が壊れるので、変更時は必ず両方を直す。**

保持すべき情報は次の4つに限られる。需要そのもの（Needs と Situation、状態、生成された Handoff）。近接検知に使う更新される識別子と、それを解決するための内部キー。待ち時間の長い順に割り当てるための発生時刻。そして受け渡しの成否。

いずれも受け渡しの完了時に破棄する。永続化する理由がない。

## 5. AI設計思想

要求定義書 §4 の AI-1 / AI-2 / AI-3 を、既存の2段階パイプラインへ対応させる。プロンプト（`lib/prompts.ts`）は前身で実運用のうえ3回チューニング済みのため変更しない（POSTMORTEM「使える部分」）。設計として明示すべきなのは、なぜ2段階に分けたかである。

ステップ1（`extractNeeds`）を乗車前の1回に限定するのは、自由記述の解読が乗車中に何度も要る処理ではないからだ。乗車後に都度呼べば応答速度が悪化するだけで、同じ入力から違う結果を得る理由がない。

ステップ2（`generateHandoff`）を［ 譲る ］が押される都度呼ぶのは、混雑度に応じた動作生成がその時の車内状況に依存し、Needs だけでは決まらないためである。混雑度は乗車前には分からない。

v4.0 では、混雑度を報告するのが受け手から譲る側に変わった（FR-04）。ステップ2の呼び出しタイミングが「受け手が要請を出した瞬間」から「譲る側が譲ると決めた瞬間」へ移る。入出力の形は変わらない。

AI-3（語気の調律）はステップ2の出力に埋め込み、別のモデル呼び出しにはしない。語気だけを独立させても追加のレイテンシに見合わない。

**却下した代替案**：ステップ1と2を1回の呼び出しに統合する案も検討した。しかし乗車前の落ち着いた入力と、車内の混雑度という動的な情報を同じプロンプトに混ぜると、混雑度が変わるたびに自由記述の解釈まで再生成させることになる。レイテンシが伸び、本人が確認済みの Needs が揺れうる。NFR-01 と確認フローの両方に反するため却下した。

### 5.1 安全設計

`containsSpeech`（`lib/speech.ts`）による発話検出とフォールバック（`lib/fallback.ts`）はそのまま使う。FR-12 はこの仕組みの要求定義であり、実装は既に要求を満たしている。

AI の非目標（診断をしない、発話を出力しない、危険動作を出力しない）は `lib/prompts.ts` に反映済みで、設計変更は不要である。

ネイティブアプリになっても**API キーはクライアントに置かない。** 生成はサーバ側で行い、アプリはそのエンドポイントを叩く。ネイティブのバイナリは解析可能であり、Web より安全にはならない（[`AGENTS.md`](../AGENTS.md) §1）。

## 7. 技術選定

### 7.1 決まったこと

**Flutter で UI を書き、BLE だけは自作のプラットフォームチャネル越しにネイティブで実装する。まず Android のみを作り、iOS は次フェーズに回す。**

Android を先にするのは、§1.5.1 で動作保証を同一OS間に絞った結果、デモを Android 2台で撮れるようになったからである。[`AGENTS.md`](../AGENTS.md) のスコープ判断（デモ動画のどのカットに映るか。映らないなら作らない）に照らすと、**Android 2台で撮る限り iOS 対応はどのカットにも映らない。** しかも Android には overflow area の問題がなく（通常のパケットで発信する）、背景での発信の制約も緩く、Mac も Apple Developer 登録も要らない。今回見つかった難所の大半が、当面は発生しない。

Flutter とネイティブの分かれ目については、次の比較を行った。

| 選択肢 | peripheral（発信）対応 | 備考 |
| :--- | :--- | :--- |
| ネイティブ（Swift ＋ Kotlin） | ○ 完全 | 2本書く手間はあるが、overflow area・背景モード・スキャンパラメータに完全に手が届く |
| Flutter | △ `flutter_ble_peripheral` は保守されている（2026年5月更新）が、**iOS 側の対応が薄い**（"iOS does not support a lot of options"） | ラッパー越しだと §1.5 級の細かい挙動で詰まったときに手が出せない |
| React Native | ✕ `react-native-ble-plx` は**2026年時点でも peripheral 非対応** | 自作ネイティブモジュールが要るので、1コードベースという利点が薄れる |

**Flutter を素で使う案も、ネイティブ2本の案も採らなかった。** 理由はこのアプリの作業量の偏りにある。UI は9画面（§3.1）で状態も単純だが、BLE と背景動作とトークン更新とモーションゲートが実装の本体になる。Flutter が節約してくれるのは軽い側であり、代わりに払うのは危ない側での不透明さになる。加えて `flutter_ble_peripheral` の iOS 側が薄いため、iOS に着手した段になって結局 Swift を書く可能性が高い。それでは Flutter にした意味が半分になる。

そこで**中間を採る。** Flutter が9画面・状態・AIサーバ呼び出しを持ち（iOS でもそのまま使える）、BLE は薄いチャネルを自分で切る。必要な口は少ない。

```
startAdvertising(token)
stopAdvertising()
startScan(serviceUUID) → (token, rssi) のストリーム
モーションゲートの有効・無効
```

汎用の BLE ライブラリは要らない。トークンを出し、拾い、RSSI を見るだけである。Android 側は Kotlin で 200〜300行程度を見込む。後から iOS へ進む際も、Swift で同じ口を実装すれば UI は書き直さずに済む。

**AI サーバは現状のまま Node / TypeScript で残す。** `lib/llm.ts`（Gemini 抽象化・実測済みモデル選定・リトライ）と `lib/prompts.ts`（実運用で3回チューニング済み）と `lib/speech.ts`／`lib/fallback.ts`（発話検証）を触らずに再利用できることが大きい。アプリはエンドポイントを叩くだけで、APIキーはサーバに留まる（[`AGENTS.md`](../AGENTS.md) §1）。

### 7.2 まだ決まっていないこと

**BLE の詳細**。サービス UUID の設計、更新される識別子の生成と解決、RSSI から距離を推定する際の閾値、背景での発信が継続する条件。

**モーションゲートの実装**（§1.4）。加速度センサーの使い方と、権限を要求するタイミング。

**受け渡しの同期手段**。ここには有力な候補がある。**2台は BLE の到達圏内にいるので、Handoff を端末間で直接やり取りできる可能性がある。** それが成立すれば NFR-02（0.5秒以内）はローカルで自明に満たされ、Pusher や Supabase のようなリアルタイムサービスが丸ごと不要になる。AI 生成（ステップ2）だけはサーバが要るので、流れは「譲る側がタップ → サーバでAI生成 → 相手へは BLE で直接通知」になる。ただし2台間の GATT 接続には別の複雑さがあるため、**§7.3 の検証項目に留める。**

### 7.3 スパイク（実装より先に行う）

手順・合格基準・落ちたときの戻り先は[`スパイク手順書.md`](スパイク手順書.md)にまとめてある。本節は何を確かめるかだけを述べる。

第一に、混雑した車内やポケットの中でも数m以内という判定が安定して出せるか。RSSI の揺れがどの程度かを実測する。ここが駄目なら隣接限定という設計の土台が崩れ、本書の §1 と §2 を書き直すことになる。

第二に、受け手のアプリを背景に置いたまま何分間発信を継続できるか。モーションゲート（§1.4）との併用が成立するかも合わせて見る。

第三に、2台間の GATT 接続で Handoff を直接渡せるか（§7.2）。成立すればリアルタイムサービスの選定そのものが不要になる。

第四に、iOS に着手する前に §1.5.1 の組み合わせ表を実機で確認する。iOS を背景にしたときに iOS の前景から本当に見えるか、Android から本当に見えないかを、推測ではなく実測で確定させる。**§1.5.1 の内容は開発者フォーラムと逆解析の記事に基づくもので、こちらで確かめたものではない。** Android のみで進める間はこの検証を保留してよいが、保留していること自体を忘れないこと。

前身の失敗は、この種の検証を「もう決まったこと」として飛ばした点にあった。

## 8. 開発フロー

### 8.1 git 運用

[`AGENTS.md`](../AGENTS.md) の git 規則をそのまま適用し、次の順序を徹底する。

実装前に関連する既存コードと POSTMORTEM の該当箇所を読む。実装は意味のある変更1つに絞り、混ぜない。検証を通してからコミットする（通らないコードはコミットしない）。デバッグして直した場合は、試行錯誤の途中経過をコミットせず、最終的に通った状態のみを1コミットにまとめる。コミット時はパスを明示し（`-A` と `.` は使わない）、メッセージには何をしたかではなくなぜそうしたかを書く。

`git reset --hard` / `git clean` / `git restore` は使わない。必要な場面が来たら実行前に確認を取る。

通常の実装は `main` に直接コミットしてよい。動作しなくなるリスクのある大きな変更は作業用ブランチを切り、検証が通ってから `main` にマージする。

### 8.2 Issue 駆動とバージョン管理

タスクは着手前に GitHub Issue を立てる。§7 の各項目、§9 のリスク項目、§10.3 のギャップ項目は、着手時にそのまま1 Issue に対応させる。Issue 本文には対応する本書の節番号を必ず書き、後から「なぜこの実装か」を設計へ遡って追えるようにする。

コミットメッセージには Issue 番号を含める。ラベルは最低限 `bug`（動いていたものが壊れた）、`design-gap`（要求定義書にない設計判断）、`spike`（§7 の未検証項目）の3種を使う。

マイルストーンはフェーズに合わせて切る。デモ直前には動作確認済みのコミットへタグを打ち、締切直前の変更で壊れた場合に戻れる基点を残す。

### 8.3 テスト方針

`lib/*.test.ts`（vitest）の `speech.test.ts` と `fallback.test.ts` はそのまま維持する。プロダクトの安全根幹にあたり、接続方式の変更と無関係である。

実機2台での通し確認は自動化しない。撮影に使う回線環境や実機に依存するテストは再現性が低く、保守コストに見合わない。手動チェックリストとして別途まとめる。

## 9. リスク

提出物は録画されたデモ動画であり、審査員の前でのライブ実演ではない。会場の通信環境やタイミングといったライブ実演固有のリスクは、撮り直しで解決するためここに含めない。残すのは**撮り直しでは解決しないもの**だけである。

| # | シナリオ | 影響 | 対策 |
| :---: | :--- | :--- | :--- |
| 1 | 近接検知が実機で安定しない（混雑時、ポケット内、RSSI の揺れ） | 隣接限定という設計の土台が崩れ、§1・§2 の書き直しになる | §7 のスパイクを実装より先に行う。**本書で最も重いリスク** |
| 2 | 混雑時の「座面に手を添えて待つ」に心理的抵抗があり、機能してもやりたくない動作になる | 撮影はできても、実運用と審査で「本当に人がこれをするか」を突かれる | 実機確認に、動作の成否だけでなく譲る側の心理的抵抗を聞く項目を加える。抵抗が大きければ混雑ブランチの動作を再設計する |
| 3 | 利用者が少ない時期、需要を発信している端末が周囲に1台しかなく、その発信自体が目立つ | 受け手の脆弱性が露出する | §1.4 の対策では解決しない。**未解決として記録する** |
| 4 | 撮影中に Gemini の無料枠のレート制限へ当たる | AI 生成が失敗しフォールバック文になり、AI が動いていないように見える映像になる | `isFallback` フラグを画面に必ず明示して隠さない。撮影直前にウォームアップし、リハーサルで挙動を把握してから本番テイクを撮る |
| 5 | 同一OS間に限るという割り切り（§1.5.1）を審査で突かれ、実用性を疑われる | 「実際には半分の組み合わせで動かないのでは」という指摘に発展する | Exposure Notification が OS レベルの API として提供された経緯（§1.5.1）を答えとして用意する。実装力ではなく Apple の設計判断に由来する壁だと説明できる |
| 6 | App Store の審査で、バックグラウンドの BLE 利用の正当性を問われる | 配布が止まる。ただしデモ動画の撮影は TestFlight で可能 | モーションゲートと発信中の明示（§1.4）が、そのまま審査への説明材料になる。FR-15 の廃止で背景スキャンが消え、説明すべき背景モードは発信の1つだけになった |
| 7 | 「デモは同一OS 2台で撮れる」という理由で §1.5.1 の制約を軽く扱い、UIへの明示を忘れる | POSTMORTEM 根本原因1（「デモだから」を検証を止める免罪符にした）の再演 | UIコピーへの明示を実装タスクとして Issue に立てる（[`AGENTS.md`](../AGENTS.md) §5）。コードコメントだけでは足りない |

## 11. スコープ外

号車をまたいだマッチングは扱わない。近接検知が数m以内に限る設計なので、車両の境界を意識する必要がない。

**iOS 版は今回作らない**（§7.1）。UI は Flutter なので、進める際に必要なのは BLE チャネルの Swift 実装と §7.3 第四項の検証である。

専用ハードウェア、ユーザー認証、決済とインセンティブは要件定義書 §3 のとおりスコープ外である。

鉄道事業者との連携（優先席の表示灯との連動、車両側インフラ）は今回も次フェーズ以降とする。
