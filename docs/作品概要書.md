# Sotto（ソット）— 席を譲りたい人が、声をかけられないまま席を渡せる

電車で席を譲る意思を持つ人は約8割いる。それでも妊娠7ヶ月の当事者が実際に座れた割合は「片手で数えるほど」に留まる。Sotto はこの差を、譲る側の恐怖を取り除くことで埋める。

## 1. 何を作るか

電車内で席を譲りたい人と席を必要としている人を、一言も交わさずに繋ぐスマートフォンアプリ。座っている人がアプリを開くと、**すぐ近くに席を必要としている人がいるかどうかだけ**が表示される。［ 譲る ］を押すと、その場の混み具合に合った身体の動きが返ってくる。立って、半歩ずれる。それで終わる。

声も、目線も、相手が本当に席を必要としているのかという判断も、どれも要らない。

## 2. なぜ「譲る側」を主役にしたか

ヘルプマークも、声かけ・サポート運動も、&HAND や May ii も、9年間ずっと譲る側に「勇気を出して声をかけよう」と呼びかけてきた。しかし調査を読むと、譲らない理由の1位は「相手に失礼になるかもしれない」46.4%（内閣府調査）で、「以前に断られた経験がある」が20.4%（エアトリ調査）を占める。

これは勇気の不足ではない。**判断を誤るリスクである。** 妊婦でなかったら失礼になる、要らないと言われたら気まずい、と考えているうちに電車は次の駅に着く。呼びかけを何年重ねてもこのリスクは減らない。

そこで Sotto は、譲る側に表示する相手を**自分から「席がほしい」と発信した人だけ**に限る。相手が席を必要としているかを推測する場面が構造から消えるので、判断を間違えようがなくなる。無言化はその上に乗る。

受け手（つわり・貧血・怪我・内部疾患などで座位が必要な人）の困難も同じ恐怖の裏返しだが、そちらには既に9年分の施策が積み上がっている。手薄なほうを狙った。

## 3. 体験

田中（22歳・学生）は座っている。目の前に立っている人が少し辛そうに見える。声をかけようとして、いつも通り固まる。

スマホを開くと「すぐ近くに席を必要としている人がいます」とだけ出ている。田中は今の混み具合を1タップで選び、［ 譲る ］を押す。画面に動作が出る。混雑時なら「立って、座面に手を添えたまま。相手が座るまでそこで待ってください」。空いていれば「立って、ポール側へ。そのまま離れて大丈夫です」。

佐藤（28歳・妊娠初期）の画面が反応する。「ごく近くの人が席を空けます」。田中が立ち、視線を外して半歩ずれる。佐藤が1〜2歩で座り、［ ありがとう ］を押す。田中の画面に「そっと伝わりました」と出る。

二人は一度も会話せず、目線も合わせない。そして田中は、一度も相手の状態を判断していない。

田中がこの画面を見て、そのままアプリを閉じてもよい。何も起こらず、佐藤は田中が見たことすら知らない。辞退ボタンは用意していない。

## 4. 先行事例との違い

| 比較項目 | ヘルプマーク | 声かけ・サポート運動 | &HAND / May ii | **Sotto** |
| :--- | :--- | :--- | :--- | :--- |
| 誰の問題を解こうとしているか | 受け手が伝えられない | 譲る側が動かない | 受け手が支援に繋がれない | **譲る側が動けない** |
| 譲る側への働きかけ | なし | 呼びかけ（啓発） | チャットで繋ぐ | **判断そのものを消す** |
| 声をかける回数 | 必要 | 必要（それが目的） | 必要 | **0回** |
| 「相手は本当に必要か」の判断 | 譲る側が行う | 譲る側が行う | 譲る側が行う | **発生しない** |

決定的な違いは最下段にある。先行事例はいずれも譲る側の判断を前提に置いたまま、その判断を下す勇気を求めてきた。Sotto は判断そのものを構造から取り除く。

## 5. なぜ生成AIが必要か

「通知と if 文で足りるのでは」という指摘への回答は3つある。

**自由記述の解読（AI-1）**。「貧血気味で立っていられない」「ギプスで座ると逆に痛い」など個人の困りごとは無限にあり、選択肢で網羅できない。自由なテキストから座位の必要性や避けたいことを構造データへ正規化する。

**混雑度に応じた身体動作の生成（AI-2）**。空いている時と超満員では正解の動作が真逆になる。空いていれば立ってすぐ離れてよいが、混雑時に離れると席を横取りされる。この分岐は本作の性格そのものを決めるダイヤルとして機能しており、事前にルール化しきれない。

**語気の調律（AI-3）**。「席を譲ってください」という命令形は義務感を生み、断る自由を奪う。善意を搾取しない語気を生成する。

加えて安全側の要件がある。出力に発話の指示が混ざるとプロダクトの存在理由が壊れるため、AIの出力はサーバー側で必ず検証し、該当したら固定文へ差し替える。ここだけはAI任せにしない。

## 6. 未解決の論点

前身のリポジトリでは、検証していない前提を確定事項として扱ったまま実装まで進んで失敗した（[`POSTMORTEM.md`](POSTMORTEM.md)）。同じことを繰り返さないため、現時点で未検証のものを明示しておく。

**近接検知の実機精度**【一部確認】。2026年9月10日に Android 実機2台で通しの受け渡しを確認し、室内・近距離では成立した（[`spike-results.md`](spike-results.md)）。RSSI で近距離と5m＋壁越しを分けられ、2台間の BLE 直結で動作データを往復させられる。ただし**距離ごとの分布、ポケットの中、混雑した車内、背景発信が何分続くかは未検証**。また受け渡しを短い間隔で連続させると接続が落ちることがあり（再接続のバックオフで回避可能）、実運用前に詰める。

**当面は同じ種類のスマホ同士でしかマッチングできない。** iOS アプリが背景に回ると、発信するサービスIDは Apple 独自の領域へ移り、Android からは検出できなくなる。したがって iPhone 同士・Android 同士では動く。しかし譲る側が Android の場合、iPhone の受け手がスマホをポケットに入れていると見つけられない。この制約は画面上にも明示する。

これは実装力の不足ではなく Apple の設計判断に由来する壁である。**接触確認アプリが OS レベルの専用API（Exposure Notification）として提供されたのは、まさにこの制約をアプリ単体では越えられないからだった。** 各国の初期の独自実装が同じ壁でつまずき、Apple と Google の API へ乗り換えた経緯がある。

**混雑時の身体動作を実際にやってもらえるか**【要確認】。「座面に手を添えて待つ」という動作への心理的抵抗は測っていない。ただし旧案（画面を緑色に光らせて席の前に立ちはだかる）は、声をかける恥ずかしさを無言で目立つ恥ずかしさに置き換えるだけだと判断して廃止し、この動作は混雑時のみに縮小した。

**利用者が少ない時期の目立ちやすさ**。需要を発信している端末が周囲に1台しかない状況では、その発信自体が目立つ。追跡防止（識別子の定期更新、電車の移動中のみ発信）は設計済みだが、この点は解決していない。
