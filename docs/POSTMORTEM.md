# Sotto 開発の振り返り（2026-09-10）

新しいリポジトリで作り直す際の引き継ぎ資料。**何が問題で、何が使えるか**をまとめる。

---

## 起きたこと（要約）

タスク1〜6を実装し、実際に人が触ってレビューした結果、3つの問題が見つかった。

1. **デザインがデモ用に見える** — 役割スイッチ・混雑度セレクタ・合言葉入力欄など、動作確認のための道具が本編の画面と同じ階層に並んでいた
2. **合言葉（ID）による接続が、企画の前提と矛盾している** — Sottoの核心は「見知らぬ他人同士が、一言も交わさずに繋がる」こと。しかし合言葉を使うには、その合言葉を**何らかの方法で相手に伝える**必要があり、これは見知らぬ他人同士では原理的に成立しない
3. **AIの意味が伝わらない** — 混雑度で動作が変わる（H-2）はコード上は実現していたが、それを目撃させる仕掛けが画面になく、「ただ短い文が出るだけ」に見えた

このうち2が最も本質的な問題であり、これを機にゼロからではなく**接続の仕組みだけを作り直す**方針に転換した。

---

## 根本原因（次に同じ失敗をしないために）

### 1. 「デモだから」を、検証を止める免罪符にした

設計書 §2.3 は「近接検知はブラウザで実装不可能。デモでは合言葉で代用する」と最初から書いていた。この判断自体は誠実だったが、実装段階で一度もこの前提を疑い直さなかった。**デモ簡略化は、書かれた瞬間から時間が経つほど「もう決まったこと」として扱われやすい。**

→ 対策：デモ簡略化を導入するたびに、画面のUIコピー上にも「これは本来◯◯の代わりです」と明示する。コードコメントだけでは実装者（AI含む）は自分のコメントを読み返さずに実装を進めてしまうため足りない。

### 2. バグ報告を受けた時、「その機能は本当に直す価値があるか」を確認しなかった

「2画面で片方しか動かない」という指摘を受け、即座に「2台同期を技術的に実現する」方向へ走った。しかし2台接続は元々 `TASKS.md` で「切ってよい範囲（タスク9）」に位置づけられた**任意機能**であり、主デモ（1画面2ペイン）はそもそも2台接続を必要としない設計だった（設計書 §6.5）。

→ 対策：バグ修正の前に「この機能はそもそも本編に必要か」を先に問う。必要ないなら、バグ修正ではなく機能の削除・格下げが正解になる場面がある。

### 3. 矛盾に気づける瞬間で、技術的な正当化に逃げた

`lib/sessions.ts` のコメントは「Vercelのサーバレスでインスタンスが分散する問題にどう対処するか」だけを書いていた。「合言葉」という言葉を選ぶ瞬間、「これは無言化という企画の核心と衝突しないか」を自問すべきだった。

→ 対策：技術的な妥当性の検証と、企画の前提との整合性の検証は別物であり、実装のたびに両方をやる。

### 4. UIが「動作確認ツール」と「実際の製品」を分離していない

役割スイッチ・合言葉入力欄が、本編の画面と同じ見た目・同じ階層で並んでいた。

→ 対策：デモ操作（審査員が触る用）と製品の実際の画面は、視覚的に明確に別の層として設計する。

### 5. デザインの「AIっぽさ」は色ではなく構造だった

一度配色を変えても、「濃紺の帯＋同一角丸パネルの繰り返し」という構造自体が、AI生成デザインによくある型（近黒背景＋単一アクセント、同一角丸カードの機械的な反復）に当てはまっていた。

→ 対策：配色より先に、同じコンポーネントを機械的に繰り返していないかを疑う。
