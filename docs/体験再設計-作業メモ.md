## 技術前提（2026-09-10 更新・大転換）

- **「Webアプリ」という前提を外した。** ネイティブアプリ（iOS/Android）でよい ―― チームがなんでも作れる
- **近接検知（数m以内の"近く"を検知）を所与のプリミティブとして扱う。** ネイティブなら BLE で実証済み（AirTag・接触確認アプリと同原理）。「近接検知は不可能」は Web 限定の話だった
- **既存の技術設計はすべて棚上げ**：Pusher（設計書 §2.7）、GPS＋号車番号（§2.3.2）、固定デモ車両（§2.4）、音響通信の可否論。技術選定は体験が固まった後の別パスで一からやる
- 背負うもの：インストール前提（デモは TestFlight／サイドロードで撮れる）、iOSビルド環境、AIパイプラインは結局サーバ側（APIキー、AGENTS.md §1 は生きる）
- これに伴い **§1 の「隣接限定」は"技術的な割り切り"ではなく"設計の意図"になった**：近くの人としか繋がない、を積極的に選ぶ

## 決まってきたこと

### 1. 再フレーム：マッチングを「隣接した人同士」に限定する

同じドア付近・2〜3m以内の人としかマッチしない。これで現行体験の気まずさ2点が同時に消える：

- 体調不良なのに車内を横断して歩く → 数歩で済む
- サポーターが席の前で画面を光らせ続ける → 隣接なら横取りの隙がほぼ無く、キープ動作が要らない

**副産物**：接続方式（同じ車両問題）が楽になる。2端末で本人確認が「会話ではなく一瞬の目視」で閉じるなら、位置推定はガバガバでよい。ズレたら「見つからない」を押すだけ。

### 2. 受け渡しの型：B案（席だけ案内・人を指さない）を採用

- サポーターは**誰も識別しない**。小さな通知 → 立つ → 一拍おいて動く、だけ
- リクエスター側だけが「近くの人が今立った」で席を特定する
- サポーター負担が A案（共有トークンを見せ合う）より軽い

**混雑時の詰め（B案の弱点対策）**：
- 超満員：AIがサポーターに「立ってポール側へ一歩。相手が座るまでその場で待つ」を出す。立ちはだかる演技ではなく「立ってすぐ立ち去らなかった」だけに見える範囲
- 空いている／混雑：「そのまま他の車両へ移動していい」
- **この指示が混雑度で正反対になること自体が、AIを使う必然性の証明**（if文で書けない）

**失敗時**：第三者が座る／席を見つけられない → 「座れなかった」1タップ → 除外して再マッチ（既存 FR-10 を流用）

### 2b. 起点：ダブル・オプトイン（→ §2d で「プル型」に更新）

- 両者がそれぞれ意思だけ表明し、近ければ system が繋ぐ
- **決め手（これは §2d でも維持）**：`要求定義書.md` §1 のサポーター最大の恐怖「相手に失礼になるかもしれない」46.4% ＝「譲ろうとしたら相手は要らなかった」という誤爆。**明示的に"ほしい"と言った人としか繋がらない**ので、この誤爆が構造的に起きない。声かけの恐怖の中核を機能ではなく構造で消せる

### 2d. 起点を「プル型」に更新（§2b を上書き）

push で譲る側に割り込まない。**譲る側が自分でアプリを開いて動く。**

- **受け手（席がほしい人）**：需要を宣言しておく
  - 慢性的に必要（高齢者・障害・内部疾患）→ **常時設定**
  - 今日だけ必要（つわり・怪我・当日の不調）→ **乗車ごとタップ**
  - どちらも同じ「近くの需要」として譲る側に見える
- **譲る側**：push 通知は受けない。譲りたい衝動が湧いたときに自分でアプリを開き、「近くに必要な人がいる」と出ていたらアクション
  - 電車内ですでに「声かけようか…」と葛藤している、その瞬間にアプリが応える。push で割り込むより自然
  - 通知不安ゼロ／行動が完全に自己起点＝主体性が最大＝「固まる人」を主役にする方向と噛み合う
- **受動サイン**（純プル型だと譲る側が「見ない」限りマッチしないので）：
  - 音・振動・push なし。次にスマホを見たとき気づく程度（バッジ／静かな常時表示等、実装形式は後で）
  - 譲る側が「そっと知らせて」を一度オンにしている前提。軽い意思表示、"Sotto" に合う
- **マッチ成立のタイミング**：譲る側がアプリを開いて「譲る」を押した瞬間。事前のプール／push は無し
- リアルタイム通信が要るのは受け渡しの一瞬だけ（譲る側が押した → 受け手の画面が即反応）

**待機画面**：受け手も譲る側も、ほぼ何も出さない＝スマホをしまえる、が理想

### 2c. お礼（ありがとうタップ）：残す。ただし「無言を成立させる部品」として

「目線も合わせない」を本気でやると受け渡しの瞬間に社会的負債が宙に浮き、どちらかが耐えきれず会釈する。**アプリ経由のお礼タップがその負債を吸収する装置**。あるから両者とも会釈から解放される。

- **リクエスター → サポーターの一方向、1タップのみ**（お礼のお礼で往復が始まるのを防ぐ）
- **言葉にしない**：マッチ時の色／記号がそっと灯る程度。サポーター側は「そっと伝わりました」くらい
- **リアルタイム**：サポーターがまだ近くにいるうちに。「成立した、もう離れていい」の合図も兼ねる
- **機能的クローズも兼ねる**：このタップで両端末リセット。一定時間タップが無ければリクエスター側に「座れましたか?」→ 座れなかった なら再マッチ（FR-10 経路）

派生（後で）：サポーターが確認前に降車／離れた場合の表示（失敗と読ませない）、「ありがとう」を文字で出すか記号だけか

### 2e. 見送りモデル（確定・プル型で作り直し）

**「見送り」という概念がほぼ溶けた。** プル型では譲る側は自分でアプリを開いたからプロンプトを見る。

- **ケース1（主）：譲るを押さずに閉じる** — 非アクション。何も起きない。受け手はこの人が見たことすら知らない。ボタン不要・コスト0・完全に不可視な"ノー"。一番きれいな見送りが機能ゼロで実現
- **ケース2：譲るを押した後にやっぱり無理**（囲まれてた／降りる駅／また固まった）→ 「やめる」を静かに用意。確認なし・理由を聞かず・探索状態に戻す。「座り直して大丈夫」（§2g H7 文言）
- **ケース3：ケース2で受け手が既に「近くの人が立ちます」を見ている** → 受け手側はそっと引っ込める。「その人は無理でした」ではなく「まだ探していますね」
- **多人数リレーは無くなる**：pingされた譲る側の列がもう無い。撤回されたら受け手の需要が"発信中"に戻り、次に「譲る」を押した人が拾う ＝ 通常フローの再開。専用のリレー機構は不要
- **無痛の原則は維持**：受け手は「誰かが助けを考えて、やめた」の痛みを一度も感じない
- **既存 FR-09 の書き換え**：「[今は難しい]→即リレー」は消える。「譲る前の非アクションは無。譲った後の撤回は理由を聞かず、受け手には『まだ探しています』だけ、静かに探索へ戻す」

### 2g. プロダクトの性格：行為重視、締めるのは混雑時だけ

「特定の1:1マッチを確実に成立させる」より、**「立ち上がる／譲る」という行為のハードルを下げる**ことを主目的に置く。1:1で繋がったかは二次的。理由：プル型（自己起点）・「固まる人」が主役・"Sotto"（取引じゃない）・譲り手の不安（"成立したか?"）をそもそも発生させない・善意を特定個人に縛らない。

ただし**横取り**（善意が実らない構造＝存在理由そのもの）を無視はできない。歯止め「成功指標＝席を必要とする人が座れた」も守る。

→ **ダイヤルは混雑度**：

- **空いている／やや混雑**：行為重視。譲り手は立つ → 席が空く → 受け手が座る。譲り手は即離れてよい。**待つ状態が無い＝ H7 が発生しない**。確認もタイムアウトも不要
- **混雑／超満員**：マッチングを締める。AI動作が「座面に手を添え、相手が座るまで待つ」に。受け手に「どの席か」がはっきり出る。H7 のタイムアウト（座り直して大丈夫）はこのブランチだけ

副産物：共通ケースのフローが軽くなる／「混雑度で挙動が正反対」がここでも出て AI の必然性が一段強くなる。

### 2h. 受け手が「席がほしい」を発信することのプライバシー・尊厳（確定）

BLEアドバタイズは公開電波。半径10m内でスキャナを持てば生パケットは拾える。漏れうるのは A: 追跡可能性、B: 「近くに体調の良くない人がいる」の可読化。

対策：
- **ローテーションする使い捨てトークン**（15分ごと等）→ 追跡は死ぬ（接触確認アプリと同じ、iOSはBLE MACも既定でランダム化）
- **モーションゲート**：常時設定＝意思。実発信は「電車の揺れを感知した時だけ」。設定は一度、露出は電車内だけ
- **ペイロード最小**：「需要モードの人がいる」＋トークンのみ。需要の中身は全部サーバ側、マッチした譲る側にだけ抽象化して渡す（AGENTS.md §3）
- **透明性**：「いま発信中」を常に表示・ワンタップ停止。隠れて発信しない
- 未解決の既知リスク：ユーザーが少ないうちは1つの需要ビーコンが目立つ

**役割の割り当て（確定）：Z ＝ 受け手・譲る側の両方が発信＋両方スキャン。** 上記の衛生対策付き。残る露出（近くのスキャナに「座りたい人アプリの利用者がいる」と分かる）は健康データでもIDでも位置履歴でもない＝低ストレス。正しく語れば「機械には可読・人間には不可視な脆弱性」＝狙いそのもの。

### 2i. 受動サインの中身 ※後に廃止

**この節の内容は採用されなかった。** iOS の背景スキャンが「間隔が疎で予測不能・1デバイスにつき単発通知のみ」で peer-to-peer 検知に使えないと判明し、FR-15 ごと廃止した（`設計書.md` §1.5.2）。Android なら実現しうるが、プラットフォーム差が体験の説明を壊すため両方で切った。**譲る側への通知は一切ない純プル型に一本化。** 以下は検討時の記録として残す。

原則（§2d）：音・振動・push なし。次にスマホを見たとき気づく程度。割り込まない。

- **`.passive` レベルのローカル通知**（iOS 15+／Android 低重要度チャンネル）：音・振動・画面点灯・バナー なし。通知リストに静かに積まれるだけ。文言「近くに、席を必要としている人がいます」。緊急感・ボタンなし
- **アイコンバッジ併用**
- **1エンカウンター1回だけ**。無視されても催促しない。受け手がBLE範囲外に出たら自動で消える
- **オプトイン**（「そっと知らせて」ON の人だけ）。デフォルトOFF ＝ 純プル型でも可、オンボーディングで薦める
- **トリガー**：「着席して5分以上 ＆ 近くに需要」。座ったばかりの人を急かさず、自然にレート制限もかかる
- **受け手側は実際の申し出が来るまでスマホは暗いまま**。「助けられる人が近くにいます」は出さない（誰も譲らなかったら残酷）。待機画面はほぼ無表示（§2d）

### 3. 主役と目標（確定）

- **主役＝譲る側**（席を譲りたいのに固まってしまう人）
- **目標＝受け手が座ること**（成功指標は「席を必要とする人が座れた」）
- 弱腰の折衷ではなく積極的な狙い：受け手の問題（頼めない）は9年分の手垢がついた土俵。譲る側の問題（やりたいのにできない）が手薄で、発案者自身が感じている問題
- 下流が全部この方向：プル型（§2d）／行為重視（§2g）／誤爆が構造的に起きない（§2b）／「そっと知らせて」を譲る側がON

**受け手のペルソナ（妊婦・つわり・貧血・怪我・内部疾患）は見出しから例に降りる。** AIステップ1の入力であって、コンセプト文には出さない。

#### コンセプト文（確定）

> **「席を譲りたい人が、声をかけられないまま、必要な人に席を渡せる。」**

- 主役＝席を譲りたい人 ／ 消すもの＝声かけ（「かけられないまま」＝固まりは直さない、固まったままで席が動く＝テーゼ）／ ゴール＝必要な人に渡る
- 採用しなかった代案：「"すみません"も"どうぞ"もなく、席が必要な人へ移る。」「譲りたいのに動けなかった人が、一言もなく席を渡せる。」

以降のすべての判断は、この1文に資するかで評価する（現 `要求定義書.md` §0 の役割を引き継ぐ）。
