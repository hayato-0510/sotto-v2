# ナレーション台本

## 0. 応募テーマ（フォームに書く1行）

**案A（推奨）**
> 席を譲りたい人が、声をかけられないまま、必要な人に席を渡せる。譲る側から「判断」を消す、生成AIの優先席マッチング。

**案B（短い）**
> 声をかけず、相手を判断することもなく、電車の席が渡る。

**案C（AIの役割を前に出す）**
> 言葉にならない困りごとを生成AIが翻訳し、その場に合う「動き方」を返す。声かけゼロで席を渡す優先席マッチング。

## B. presentation 動画（約3分／スライド10枚）

`docs/作品概要書スライド.pdf` を尺つきの動画にしたものへ、声を当てる。
各スライドの表示時間は下の「尺」に合わせてある（`demo/presentation-slides.mp4`）。

### スライド1　タイトル（12秒）

Sotto。席を譲りたい人が、声をかけられないまま、必要な人に席を渡せる。
電車の優先席マッチングアプリです。ユメカタリ生成AIコンテスト、開発部門への応募作品です。

### スライド2　解こうとしている問題（22秒）

電車で席を譲る意思を持つ人は、約8割います。それでも、妊娠7ヶ月の当事者が実際に座れた割合は、片手で数えるほどに留まります。
譲らない理由の1位は「相手に失礼になるかもしれない」で、46パーセント。「以前に断られた経験がある」が20パーセント。
これは勇気の不足ではありません。判断を誤るリスクです。何年呼びかけを重ねても、このリスクは減りません。

### スライド3　何を作るか（18秒）

座っている人がアプリを開くと、すぐ近くに席を必要としている人がいるかどうか、それだけが表示されます。
譲るを押すと、その場の混み具合に合った身体の動きが返ってきます。立って、半歩ずれる。それで終わりです。
声をかける工程も、目線も、相手は本当に必要かという判断も、どれも要りません。

### スライド4　設計の中核（20秒）

これまでの取り組みは、9年間ずっと譲る側へ「勇気を出して声をかけよう」と呼びかけてきました。
どれも、譲る側の判断を前提に置いたまま、その判断を下す勇気を求めています。
Sotto は、譲る側に表示する相手を、自分から「席がほしい」と発信した人だけに限ります。
相手が席を必要としているかを推測する場面が、構造から消えます。だから、判断を間違えようがない。無言化は、その上に乗ります。

### スライド5　体験（24秒）

受け手の佐藤さんは、アプリで「席がほしい」とだけ発信しておきます。
譲る側の田中さんの画面に「すぐ近くに、席を必要としている人がいます」と出る。混み具合を1タップして、譲るを押す。
生成AIが、その場に合った動作を返します。同じ瞬間、佐藤さんの画面が「ごく近くの人が席を空けます」に変わる。
田中さんが立ち、視線を外して半歩ずれる。佐藤さんが座って、ありがとうを押す。
二人は一度も会話せず、目線も合わせていません。そして田中さんは、一度も相手の状態を判断していません。

### スライド6　先行事例との違い（20秒）

先行事例との違いは、この表の最下段にあります。
ヘルプマークも、声かけ運動も、&HAND も、「相手は本当に必要か」の判断は譲る側が行う前提でした。
Sotto では、その判断が発生しません。声をかける回数はゼロ。判断そのものを、構造から取り除いています。

### スライド7　なぜ生成AIが必要か（26秒）

「通知と if 文で足りるのでは」という指摘への回答は3つあります。
1つ目、自由記述の解読。困りごとは無限にあり、選択肢で網羅できません。自由な文章を、構造データに正規化します。
2つ目、混雑度に応じた身体動作の生成。空いている時と超満員では、正解の動作が真逆になります。この分岐は事前にルール化しきれません。
3つ目、語気の調律。命令形は義務感を生み、断る自由を奪います。善意を搾取しない語気を生成します。
加えて、出力に発話の指示が混ざらないか、サーバ側で必ず検証します。ここだけは、AI任せにしません。

### スライド8　実装状況（20秒）

AIサーバは Next.js で、Vercel で稼働しています。状態を持たず、需要はサーバ鍵で封緘して、受け手の端末が持ちます。
アプリは Flutter で、BLE だけ自作のネイティブチャネルで書いています。受け渡しの同期は BLE 直結で確定し、リアルタイムサービスは不要になりました。
Android 実機2台で、役割選択から受け渡し、お礼まで、通し確認が成立しています。

### スライド9　未解決の論点（22秒）

検証していない前提を、確定事項として扱わないようにしています。
近接検知は、室内・近距離では実機で成立しました。距離ごとの分布、ポケットの中、混雑した車内は、まだ未検証です。
当面は同じ種類のスマホ同士に限られます。これは Apple の設計判断に由来する壁で、接触確認アプリが専用APIになったのと同じ理由です。
混雑時の動作を実際にやってもらえるか、利用者が少ない時期の目立ちやすさも、残った課題です。
